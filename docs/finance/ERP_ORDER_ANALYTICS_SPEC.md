### 2.1.1 财务订单时间字段的统一格式（用户 2026-10-14 新要求）

- **所有日期时间字段**在本模块的前端列表、详情、统计大屏时间信息、日志、接口可见展示和 Excel 导出中统一显示为 **`YYYY-MM-DD HH:MM:SS`**，如 `2026-11-10 08:30:00`，24 小时制，固定两位秒。
- 业务字段 `订单日期`、`预交货日` 必须保留 E10 源日期时间的真实小时、分钟和秒；不能像现有 `finance-order-fields.json` 的 `CONVERT(char(10),...,23)` 一样仅导出日期，**不能在已截断的 `YYYY-MM-DD` 后面直接虚构 `00:00:00` 冒充源真实时间**。请先核实 E10 `ORDER_DATE` 和 `PLAN_DELIVERY_DATE` 的源 SQL 类型/真实数据；对本身只有日期精度的源数据，若产品需要固定格式可显示 `00:00:00`，但在源字段映射/验收报告中标注该时间分量并非已核实的真实业务时刻，不可据此计算小时级交期。
- `预交货日` 的订单级取值仍使用**同单品项最早的有效非空原始日期时间**（`MIN`），精确比较到秒；不得改回多日期冲突置空。品项原始时间不覆盖。
- `年月` 是业务月份，**始终保持 `YYYY-MM`**，比如 `2026-11`；年度/月份选择器仍使用业务月份。仅用于日期范围选择的输入可保留 `YYYY-MM-DD`，但返回的日期时间数据统一按19字符完整格式展示。
- 源日期时间按 E10 **Asia/Shanghai 业务本地时间口径**处理，不可将无时区的 SQL Server datetime 直接当成 UTC 再无依据转换+8小时。PostgreSQL/JSON 的时间类型与格式应保持确定且不丢秒；必要时以**新增** migration 更新派生视图、字段类型或安全迁移，严禁修改已经生产执行过的历史 migration。
- 涉及真实现有数据，应完成受控重新读取/投影，使既有订单可展示真实时分秒；只把 UI 格式改为带时分秒不足以验收。验证 E10 源值、原始明细、月度聚合（包括254张多交期订单）、页面、API、Excel 导出各环节一致；不改变订单数、汇总金额及客户分类。
- 前端若使用 Day.js，格式 token 应写为 `YYYY-MM-DD HH:mm:ss`（**小写 `mm` 是分钟，小写 `ss` 是秒**）；用户需求中的 `YYYY-MM-DD HH:MM:SS` 是展示约定写法，不可把大写 `MM`/`SS` 直接交给 Day.js。

### 2.2 派生业务表：月度数据（9列，**销售订单级**）

表头与顺序固定：

`年月｜客户编号｜单号｜订单日期｜预交货日｜本币总金额｜客户单号｜事业部划分｜国内外划分`

转换规则：
1. 源明细按 `tenant + E10来源 + 单号` 分组为一条销售订单（如果 E10 编码证明不同账套共享单号，则来源账套亦纳入唯一键；不能跨来源误合并）。同一个单号多个“品项/序号”**要相加，不得只取首行或把整单重复计数**。
2. `本币总金额 = SUM(对应有效品项.本币合计金额)`，精确到分。数据直接取E10真实品项，不读取Excel/重复计算汇率；本币具体币别须在E10账号配置中验证。
3. 同一订单的客户编号、年月、订单日期、客户单号如存在非空互相冲突，应输出异常并阻止该订单无提示自动归并；不可任取首行。**用户2026-10-14最新确认：同一订单多个品项的`预交货日`不一致时，订单级`预交货日`统一取所有有效、非空预交货日期中最早的一个（MIN）；不得再因多交期置空或列为阻断性冲突。**如全部品项的`预交货日`均为空，订单级才留空；部分为空、部分有日期则取非空日期中的最早值。原始品项日期一律保留、不得覆盖。多交期订单可作为非阻断性数据质量提示计数，不影响整单金额、订单数及大屏统计。
4. `年月` 优先保持 E10 导出的业务年月；与订单日期月份不同，标出差异供复核，不擅自更改业务周期。所有按年/月统计必须使用同一规范化后的“年月”字段。
5. `事业部划分`、`国内外划分` **只能**以 `tenant_id + 完整客户编号` 精确 JOIN 已有 `finance_customer_mappings`：分别读取 `department_category`、`sales_channel`。不能使用 ERP “销售部门名称”、订单号前缀、客户编号前缀或 PMC 事业部映射进行推断。
6. 财务字典来源 `packages/contracts/src/finance.ts`：`业务一部/业务二部/业务三部/业务四部` 和 `内销/外销`。数据存储/规则用 `内销`，如按模板展示 `国内`，仅做受控展示映射（`内销 → 国内`），不能保存混乱的两种内部枚举。
7. 未匹配客户或两个分类任一为空：展示“待分类”并提供“未分类客户数/订单数/金额”，金额仍计入**订单总额**，但不强行归到某事业部或内外销；财务人员应去已有客户对应表补全，禁止本次导入自动改写客户分类。推荐报表口径为**当前财务客户分类**，映射修正时历史分析随之更新并标识“按当前分类”；若需要财务关账锁定快照另提专项方案。
8. 允许金额为0的订单记录；负数、重复序号、异常金额、跨读取批次重叠、同一订单不一致须进入复核，禁止静默删除。
9. 严格保留模板9个中文表头及顺序：`年月`、`客户编号`、`单号`、`订单日期`、`预交货日`、`本币总金额`、`客户单号`、`事业部划分`、`国内外划分`。原始品项金额字段叫 `本币合计金额`，订单级汇总叫 `本币总金额`，不得混称。

### 2.2.1 既有 E10 订单标准SQL优先级（用户补充）

- 生产服务器已有标准订单SQL目录：`/data/automation/code/sql/E10/`，既有 `automation/customer_import/readers/e10.py` 确认读取 `/data/automation/code/sql/E10/sales_order.sql`。财务模块当前 `data-operations/e10/finance_order_reader.py` 使用自行拼接的E10 SQL和字段字典，并**未引用该标准SQL**。
- 开发和验收必须首先在服务器本机阅读上述标准SQL，核对其订单头、明细、交期、金额、审核及指定结束等业务规则，再与财务34字段及汇总逻辑逐项比对。以**用户已有标准SQL的业务语义为优先核查依据**，但须确认真实SQL是否确实包含“指定结束”的完整排除口径；不能臆断标准SQL已经覆盖此规则。
- 满足2025-01-01（含）订单范围、完整中文字段、订单级金额与秒精度日期的前提下，优先复用标准SQL已有的成熟查询逻辑。新增财务模块特有过滤应独立、安全、可追踪，不能修改标准SQL文件或它的旧调用方来间接破坏其他系统；不得仅因为两段SQL字段相近就声称结果口径相同。

**统计大屏信息展示简化（2026-10-14）**：不展示“多个预交货日 N 张，订单级预交货日已取最早日期”，也不展示旧版“预交货日冲突 N 张，整单金额已纳入统计，预交货日留空”等横幅；此前要求隐藏的待复核金额横幅同样不再显示。订单级 `预交货日` 继续按同订单所有有效非空时间最小值（MIN）计算；原始品项时间、报表金额、订单数、异常追踪与授权管理员的诊断数据均保持，不允许为了隐藏提示改变后端统计或丢弃记录。

### 2.3 待复核与“指定结束”订单（用户 2026-10-14 最新规则）

1. **待复核订单默认不参与统计**：沿用现有 `finance_e10_monthly` 的异常排除门禁（如业务字段冲突、重复序号、来源缺失、源字段异常），不改变待复核业务定义。统计大屏**不再显示**“待复核订单 X 张，金额 X 元，暂未纳入统计”这一警告横幅；后端可继续保留经授权的异常流水与内部核查指标，不能因此把待复核订单纳入统计。
2. **“指定结束”订单完全排除财务统计**：无论已产生多少品项/金额，只要 E10 的真实业务状态经核实确认为该订单属于**指定结束**，整张订单不进入 `月度数据`、`统计大屏`、国内/外销金额、事业部汇总、客户排行、月度趋势、同比环比及其导出；不得仅在前端隐藏行或警告。
3. **先核实真实 E10 状态来源与枚举**：目前财务 `结束码` 可见列读取 `SALES_ORDER_DOC_SD.[CLOSE]`（通过交货计划聚合），而现有 ERP staging 还读取订单头 `SALES_ORDER_DOC.[CLOSE]`。Codex 必须在授权环境中只读核实 `SALES_ORDER_DOC.[CLOSE]` 与 `SALES_ORDER_DOC_D`、`SALES_ORDER_DOC_SD.[CLOSE]` 的真实状态值/字典含义，用已确认的源代码或数据样本确定“指定结束”的**准确标识以及整单还是品项/计划层级**。不能臆测其值是字符串“指定结束”，也不能把所有“已结束”“正常完成”“已结算”都排除。
4. **推荐处理层级**：保留`系统导出`的ERP原始品项作溯源（保留34列原中文表头）；新增必要的**内部**订单头结束状态字段，建立统一的`是否指定结束`合格性判定；在后端财务订单汇总视图/查询中统一排除，不改变现有 ERP/PMC 权威订单表。若实际 E10 明确指定结束是订单级，整单排除；若来自品项/交货计划，先确认如何升格到整单，不允许自行用“任一品项结束”误删订单。
5. **数据对账**：源 E10 品项全量金额与纳入统计金额不再直接相等，应分成“E10 原始订单金额 / 指定结束排除金额 / 待复核排除金额 / 有效统计金额”，并明确互斥分类或去重归因规则。四组大屏指标、月度数据、导出与对比均按同一有效订单集合计算。财务管理员可在受限诊断/验收结果中复核排除的订单数量和金额，但不在统计大屏展示待复核金额警告。
6. **初始化和增量**：自2025-01-01起的历史订单要重新评估指定结束状态；未来订单由未结束转为指定结束或反向变更时，受控刷新需重新计算归属与统计，不得重复计额；不得擅自修改现有 ERP 同步任务。

## 3. E10 系统直连、初始化、增量与安全

- **数据源**：系统数据（E10），不使用上传Excel初始化、不设置文件上传/预检/人工导入流程。原模板只用于验收中文字段名称、列顺序、计算口径、大屏维度；系统页面可以提供Excel**导出**，但不能把导出文件作为系统的数据源。
- **初始化范围**：`订单日期 >= 2025-01-01`（含当日）。分页读取E10真实订单品项，稳定业务键防重复，持久记录游标/批次/数量/金额/异常；要求2025历史完整且可与2026比较。
- **数据复用**：优先调查KDOS既有 `erp_staging_*`、`sales_orders` 可用字段、来源和2025年覆盖范围；不足的字段/时间段通过受控 `basic_code.MSSQLDatabase` 只读查E10补齐，不修改现有自2026年开始的通用ERP同步起点、不新增另一套权威订单数据。
- **增量刷新**：按ERP真实最后修改字段与来源稳定主键（通过只读验证后才使用）幂等增量，更新品项后重算订单级金额；源缺记录不能直接当作取消订单。第一期只支持授权手动刷新，周期性n8n触发需另行授权。
- **隔离与权限**：财务专用受控读模型、Finance Application Command/受控API、租户RLS、字段权限、审计、事务和非并发锁；源库绝对只读，凭据沿用`basic_code`受限配置。不得修改财务客户对应表、PMC映射、ERP正式订单、主计划、当前systemd/n8n任务。
- **报表页面**：“系统导出”展示34列E10品项、“月度数据”展示9列订单汇总、“统计大屏”显示同源聚合；均复用公共分页、过滤、排序、导出、中文字段元数据，不在前端加载全年全量数据。
- **财务分类**：`tenant_id + 完整客户编号` 精确关联 `finance_customer_mappings` 的 `department_category`、`sales_channel`；不修改客户原始分类，未匹配进入“待分类”并计入总金额。
## 4. 统计大屏（模板要求必须全部落地）

数据口径统一为选定时间范围、租户/权限范围内的**本币含税订单金额**，不是到账金额、开票金额或会计营业收入；数据从同一订单级来源聚合，不能人工维护四套统计数据。

### 必须实现的4组

1. **国内/外销**：金额（元或万元）、所选年度占比、合计；内销前端可称“国内”，必须有“待分类”可见项，不得金额消失。
2. **事业部**：业务一部、二部、三部、四部金额与占比，全年合计；没有订单也可显示0，不得仅支持前三个部门。
3. **客户年度金额排名**：按完整客户编号汇总、金额降序、占比、TOP 10/20及明细列表；保留查询全部客户和导出能力，不因后缀相似而合并。
4. **1—12月趋势**：每月订单额（元、万元）与合计；空月显示0，趋势图+表格统一后台指标。
