# 四部追踪表 Web 应用：可直接交给 Codex 的开发提示词（V2）

> 使用方法：把 `4部追踪表_web.2.xlsx` 放到准备开发的项目目录中，然后将下面“提示词正文”完整发送给 Codex。首次运行前只需准备好 PostgreSQL 的主机、端口、用户名和密码，不要把真实密码写进 Git。

## 提示词正文

你现在要在我的 Windows 电脑上，从零开发一个“生产主计划与四部追踪”Web 应用。请直接在当前工作目录实施，不要只输出架构建议或伪代码。你要持续开发、运行、测试和修复，直到 V0.1 验收项全部通过。

### 一、当前电脑环境与硬约束

当前已知环境：

- 操作系统：Windows，原生开发，不使用 WSL。
- Node.js：`v22.23.2`。
- npm：`10.9.8`。
- pnpm：`11.20.0`。
- PostgreSQL：假设已经安装并作为 Windows 服务运行。
- 当前没有 Docker，也不要求安装 Docker。
- 当前没有 MinIO，也不要求安装 MinIO。
- npm 网络代理可能为 `http://127.0.0.1:7890`；只有依赖下载确实失败或过慢时才检查现有代理配置，不要擅自长期关闭 SSL 校验。

必须遵守：

1. 所有本地开发、数据库迁移、测试和启动命令都必须能在 Windows PowerShell 中运行。
2. 不得依赖 Bash、WSL、Docker、Linux 专用路径或 Linux 专用命令。
3. 所有脚本使用 Node.js、pnpm 或 PowerShell，并保持跨平台路径写法。
4. 不要重装或切换 Node.js、pnpm、PostgreSQL。
5. 不要引入任何付费组件、试用版组件或需要商业授权才能上线的功能。
6. 前端只允许使用 `ag-grid-community`，禁止安装或间接引入 `ag-grid-enterprise`。
7. PostgreSQL 是唯一业务数据源；Excel 只用于初始化、导入、导出和人工核对，不能作为运行时数据库。
8. 密码、JWT 密钥和 API Key 只能放进被 Git 忽略的 `.env`；仓库只提交 `.env.example`，不得在文档中记录真实数据库密码。

开始时先执行并记录结果：

```powershell
node -v
npm -v
pnpm -v
psql --version
Get-Service | Where-Object { $_.Name -match 'postgres' -or $_.DisplayName -match 'postgres' }
```

只有数据库连接参数或密码确实无法获知时，才向我询问这一项；其他技术决定自行采用本提示词的默认值继续。

### 二、源 Excel 的使用规则

源文件名：

```text
4部追踪表_web.2.xlsx
```

先在当前目录及子目录查找该文件。如果没有找到，只询问我一次它的完整 Windows 路径。

读取 Excel 时只把以下内容作为需求依据：

- Sheet 名称；
- 第一、第二行表头；
- 已有数据的类型、重复关系、空值情况和枚举值；
- 字典表与供应商名单中的非空值。

不要把源文件中的公式、随机数、样式、条件格式、合并单元格、缓存结果、错误值或隐藏残留当成业务规则。尤其不要恢复、照搬或依赖 `RANDBETWEEN`、`#REF!`、`#VALUE!` 等内容。若单元格是公式，只能在导入预览中显示其缓存值和“来源为公式”的警告，不能执行 Excel 公式。

### 三、已经确认的 Excel 数据结构

工作簿共有 4 个 Sheet：

1. `滚动主计划`：订单级汇总视图，12 列。
2. `8月计划`：订单品号级月度计划，A:BY，共 77 列，双层分组表头。
3. `供应商名单`：供应商名称及重复检查。
4. `字典表`：8 类枚举值。

#### 1. 滚动主计划字段

`序号、订单号、下单日期、客户要求交期、产前评审交期、异常后二次交期、异常交期交货方式、总数量、已完成数量、待完成数量、完成比例、所属事业部`。

这里不能建立独立的重复业务表。它必须由订单和订单品号数据实时汇总生成，允许筛选、排序和导出，但普通用户不能直接修改汇总数。

#### 2. 月度计划的普通字段

`序号、订单号、下单日期、客户要求交期、产前评审交期、异常后二次交期、异常交期交货方式、装柜日期、新旧款、品号、关联信息、品名、简图、产品属性、表面性质、特别项、生产数量、历史入库数据、当天入库数、订单欠数、处理方式`。

末尾普通字段：

`对应计划页数、订单异常信息、验货、验货数量、备注、订单周数、月、单价、订单入库金额、订单欠数金额、客户、所属事业部`。

#### 5. 字典初始值

- 新旧款：`新、旧`。
- 产品属性：`五金、木作、五金+木作`。
- 表面性质：`烤漆、电镀`。
- 特别项：`亚克力`。
- 处理方式：`自制、外协`。
- 外协方式：`成品外协、毛坯外协、工序外协`。
- 事业部：`事业一部、事业二部、事业三部、事业四部、贻居、电镀厂`。
- 交货方式：`空运、海运、汽运、火车、内河船运、其他`。

供应商名单导入时：跳过空行，全部按字符串保存，去除首尾空格，禁止重复。纯数字名称或疑似事业部名称只作为“数据质量警告”，不要擅自删除。

#### 6. 数据特征与类型要求

- 一个订单可对应多个品号；订单号在月度计划中会重复。
- `订单号、品号、关联信息、供应商名称`必须按字符串保存，不能转换成数字或丢失前导零、斜杠、连字符。
- `关联信息`默认由`订单号 + 品号`生成并只读，但数据库仍应建立明确唯一约束，不要只依赖字符串拼接。
- 日期要把 Excel 序列值转换成真正的日期；前后端统一传 ISO `YYYY-MM-DD`，数据库使用 `date`，不要受本机时区影响而前后偏移一天。
- 数量使用整数或足够精度的 decimal；`所需天数`必须支持 `0.5` 等小数。
- 金额使用 PostgreSQL `numeric`，不能用 JavaScript 浮点数直接做最终金额计算。
- 现有“状态”样本可能包含 `Y`、数字或空值，因此 V0.1 先按可配置字符串处理，不要强制改成布尔值。
- 绝大多数字段允许为空；后端不能把空字符串、`null`、数字 0 混为一谈。
- `简图`现有错误值不代表有效图片。V0.1 将其设计为可空的图片相对路径或 URL；本地上传文件存入项目可配置的数据目录，数据库只存元数据。通过存储接口隔离实现，未来可以替换为 MinIO/S3，但本阶段不安装 MinIO。单字段最多只上传2张图片，如果超过3M，则压缩后再上传。

### 四、目标技术架构

采用一个 pnpm workspace，不使用复杂脚手架：

```text
apps/
  web/        React + Vite + TypeScript
  api/        NestJS + TypeScript
packages/
  shared/     DTO 类型、字段键、权限键、字典与表头定义
docs/
scripts/
```

技术选型：

- 前端：React、Vite、TypeScript、React Router、TanStack Query、Ant Design、AG Grid Community。
- 后端：NestJS、TypeORM、PostgreSQL 驱动、class-validator、JWT、Swagger/OpenAPI、Socket.IO Gateway。
- Excel：后端使用 ExcelJS 读取和生成 `.xlsx`；禁止在浏览器端直接信任 Excel 数据。
- 测试：前端 Vitest，后端 Jest + Supertest，端到端测试 Playwright。
- 日志：结构化日志，至少包含 requestId、用户、操作、对象和结果；不得记录密码和完整 Token。

所有依赖选择当前与 Node.js 22 兼容的稳定版，固定到 `pnpm-lock.yaml`。不要为了追求“最新”使用 beta、rc、canary 或 nightly 版本。

### 五、核心数据库模型

用 TypeORM migration 创建数据库，不得在开发之外使用 `synchronize: true`。

至少包含以下实体：

1. `users`：账号、姓名、密码哈希、启用状态、所属事业部、最后登录时间。
2. `roles`、`user_roles`。
3. `permissions`：角色、资源、字段键或字段组键、read/create/update/delete/import/export 权限。
4. `role_data_scopes`：角色可访问的事业部范围；管理员可为全部。
5. `plan_periods`：年度、月份、状态，唯一键 `(year, month)`；不要把“8月计划”硬编码成数据库表名。
6. `orders`：订单级日期、交货方式、客户、事业部和 `version`。
7. `order_items`：所属订单、计划期间、品号、产品信息、数量、入库、价格、验货、异常、备注和 `version`。
8. `outsourcing_details`：订单品号的一对一外协信息。
9. `process_definitions`：14 个工序组的 code、名称、排序，以及是否启用所需天数/交期/状态/异常字段。
10. `item_process_progress`：`order_item_id + process_definition_id` 唯一；保存所需天数、交期、状态、异常和 `version`。
11. `dictionary_types`、`dictionary_values`：字典类别、值、排序、启用状态，值在同类别内唯一。
12. `suppliers`：名称唯一、启用状态、备注。
13. `audit_logs`：操作者、时间、资源、记录 ID、动作、变更前后 JSON、requestId、来源（web/api/import）。
14. `api_keys`：名称、哈希、权限范围、到期时间、最后使用时间；不得明文保存密钥。
15. `import_jobs`、`import_job_errors`：导入文件、状态、统计、逐行错误和发起人。

数据库必须使用外键、唯一约束、检查约束、必要索引和事务。订单号与品号可重复出现于不同计划期间时，唯一规则要通过业务键清晰表达，并写测试证明不会误覆盖历史数据。

### 六、明确的计算与数据责任

只实现能从标题和样本明确确认的计算：

- 品号欠数：`生产数量 - 历史入库数据 - 当天入库数`，空数量按 0 参与；若结果小于 0，保留真实结果并产生数据质量警告，不要静默截断。
- 订单总数量：订单下所有当前有效品号的生产数量合计。
- 已完成数量：订单总数量减去订单待完成数量。
- 订单待完成数量：品号欠数合计。
- 完成比例：总数量为 0 时返回 `null`，否则为已完成数量/总数量。
- 订单入库金额：`(历史入库数据 + 当天入库数) × 单价`。
- 订单欠数金额：`订单欠数 × 单价`。

这些计算必须集中在后端领域服务中并有单元测试；前端只显示后端结果。不要根据源 Excel 残留公式推断工序交期、工序状态、订单周数或月份的生成规则。V0.1 中这些字段作为可编辑/可导入数据，后续再接 E10、MES 或专门规则。

### 七、V0.1 必须完成的功能

#### 1. 登录与权限

- 用户名密码登录；密码使用 Argon2 或等价安全哈希。
- JWT 短期访问令牌 + 安全刷新机制。
- 初始角色：系统管理员、计划员、事业部编辑、工序编辑、只读用户。
- 权限必须由后端强制执行，前端隐藏/只读只是界面表现。
- 支持 Sheet/资源、字段组、单字段、操作、事业部数据范围控制。
- 工序编辑人员可以被限制为只编辑指定工序组，不能通过手写 API 修改其他列。
- 无权查看的字段不能出现在 API 响应、Excel 导出和 WebSocket 消息中。

#### 2. 月度计划页面

- 选择年、月后加载对应计划期间。
- 还原 Excel 的双层分组表头和 77 列顺序，但界面无需模仿 Excel 样式。
- 使用横向虚拟滚动；固定序号、订单号、品号、品名等关键列。
- 支持筛选、排序、搜索、列显示/隐藏、列宽调整、个人视图保存。
- 支持单元格编辑、下拉字典、日期选择、数字校验、批量粘贴和批量保存。若 AG Grid Community 不提供所需的粘贴能力，使用浏览器 Clipboard API 和自定义 TSV 解析实现，禁止因此引入 Enterprise 包。
- 编辑提交以单元格或小批次为单位，失败时明确标出失败字段，不得整页静默失败。
- 状态、异常、欠数使用清晰但克制的颜色提示。

#### 3. 滚动主计划页面

- 由订单和品号明细实时聚合，不维护重复汇总数据。
- 支持按事业部、客户、交期、订单号、完成比例筛选。
- 点击订单展开或跳转到对应品号明细。
- 汇总数量、金额和完成比例由后端返回。

#### 4. 基础资料与系统管理

- 供应商管理、字典管理、工序定义管理。
- 用户、角色、字段权限、事业部数据范围管理。
- 审计日志查询，支持按用户、日期、订单和动作筛选。

#### 5. Excel 导入导出

- 上传后先预览和校验，显示将新增、更新、跳过、警告和失败的数量，用户确认后才在事务中写入。
- 识别上述 4 个 Sheet；月度 Sheet 名允许是“8月计划”这类名称，但年份和月份必须由用户确认或从明确字段取得，不能凭当前日期猜测。
- 精确映射 77 个字段及 14 个工序组。
- Excel 日期、公式缓存、错误值、空字符串、数字文本都要有明确转换规则。
- 导入采用业务键幂等 upsert，同一文件重复导入不得产生重复记录。
- 导出必须生成双层表头的月度计划，以及单层表头的滚动主计划、供应商、字典表。
- 导入失败必须能下载错误清单；不能出现部分成功但界面显示全部成功。

#### 6. 协同编辑与冲突

- `orders`、`order_items`、`item_process_progress`使用整数 `version` 做乐观锁。
- 更新请求必须携带 `expectedVersion`；版本不一致返回 HTTP 409，并返回当前服务器值、用户提交值和冲突字段。
- 通过 NestJS WebSocket Gateway 广播已提交的变更；只向有权限且正在查看相应期间/事业部的用户广播。
- 不实现 Excel 单元格 OT/CRDT；当前是业务记录协同，不是多人共同编辑同一个 XLSX 文件。

#### 7. 自动化与开放 API

- REST API 前缀 `/api/v1`。
- Swagger UI 路径 `/api/docs`，同时输出可下载的 OpenAPI JSON。
- 提供订单、品号、工序进度、供应商、字典、批量更新、导入任务、审计日志 API。
- 人员使用 JWT；外部系统使用带权限范围和到期时间的 API Key。
- 批量写入支持 `Idempotency-Key`，防止 N8N、E10 或其他系统重试造成重复数据。
- 所有自动化写入同样执行字段权限、数据范围、校验、乐观锁和审计。
- 本阶段不要硬编码鼎捷 E10 数据库表或接口，只提供稳定的集成边界和示例调用。

#### 8. 页面视觉效果

- 左侧有标签组，其中一组为主计划，主计划有2个页面，一个是“滚动主计划”，另一个也是标签，是“2026年月度计划”，2026年月度计划标签里，有一个页面“8月计划”。

### 八、Windows 本地启动体验

提供：

- `.env.example`；
- `scripts/setup.ps1`：检查环境、安装依赖、创建/检查数据库、运行 migration、seed 初始数据；

建议根脚本至少包括：

```text
pnpm install
pnpm db:migrate
pnpm db:seed
pnpm dev
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm build
```

首次 seed 生成管理员时，不要在仓库里写固定密码。允许通过环境变量传入，或生成一次性随机密码并仅在终端显示一次，首次登录强制修改。

### 九、实施顺序

按以下阶段实施，每完成一阶段就运行相应检查并更新 `docs/progress.md`：

1. 检查环境和源 Excel，输出实际字段映射报告。

5. 完成月度计划 77 列双层表头、查询、编辑和后端校验。

### 十、V0.1 验收标准

只有以下全部满足才算完成：

- Windows PowerShell 中可以一条命令启动开发环境。
- 前后端编译通过，lint、typecheck、unit、API integration、Playwright 核心流程测试通过。
- PostgreSQL migration 能从空数据库完整执行，seed 可重复运行且不产生重复数据。
- 能导入 `4部追踪表_web.2.xlsx` 的非空业务数据，日期、文本标识和 14 个工序组映射正确。
- 月度计划显示 77 列双层表头，并能顺畅横向滚动、筛选和编辑。
- 一个订单多个品号时，滚动主计划汇总数量和完成比例正确。
- 两个用户同时修改同一记录时，后提交者收到可理解的 409 冲突提示，不覆盖先提交数据。
- 事业部用户无法读取或修改越权记录；工序用户无法修改未授权字段组；直接调用 API 也无法绕过。
- 所有修改都能在审计日志中追溯。
- Excel 导入有预览、确认、错误明细和幂等保护；导出能重新生成相同业务结构。
- Swagger 中可测试主要 API，API Key 权限和幂等写入有自动化测试。
- 不依赖 WSL、Docker、MinIO、Univer、AG Grid Enterprise 或其他付费组件。
- `README.md` 能让没有参与开发的人在这台 Windows 电脑上完成配置、启动、登录、导入和备份。
