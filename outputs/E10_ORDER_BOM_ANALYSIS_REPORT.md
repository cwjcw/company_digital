# E10 销售订单至 BOM 生成耗时分析

**调查时间：** 2026-11-09（Asia/Shanghai）
**范围：** 只读核查 E10 订单、品项、BOM、有效期和工程变更数据；不写 E10 或 KDOS，不部署、不迁移。
**可复核 SQL：** [E10_ORDER_BOM_ANALYSIS_READONLY.sql](E10_ORDER_BOM_ANALYSIS_READONLY.sql)

## 结论摘要

- 订单品项可通过 `SALES_ORDER_DOC_D.ITEM_ID = ITEM.ITEM_BUSINESS_ID` 关联品项；BOM 母件可通过 `BOM.ITEM_ID` 关联同一品项。BOM 适用组织还须匹配 `ITEM_PLANT.Owner_Org_ROid`。这是 UUID 业务键关联；本次元数据核查未发现这些核心表之间声明的 SQL Server 外键。
- 订单下达的候选时间是已审核订单头 `SALES_ORDER_DOC.ApproveDate`；`ORDER_DATE` 是业务订单日期，`CreateDate` 是记录创建时间。哪个等于公司定义的“下达”仍需业务确认。
- BOM 首次建立可读 `BOM.CreateDate`，头表通过审核的时间可读 `BOM.ApproveDate`。当前可按 BOM 头审核状态和子件有效期判断“此刻是否可用”；但现有数据不能对所有 BOM 准确还原历史结构第一次完整的时间。
- 抽样 30 个订单品项（28 张订单）：24 个依现有 E10 物料规则需 BOM；其中 16 个当前有一个已审核且至少含一条当前有效已审核明细的 BOM，8 个在匹配组织下未找到 BOM。另 6 个是 `ITEM_PROPERTY=P` 且 `ITEM_ROUTING_CONTROL=0`，现有规则判为研发/BOM 不适用。该“完成”只是当前系统结构与审核口径，不代表图纸齐全或业务上绝无漏料。
- 24 个适用品项中，14 个可按当前数据标为订单审核前已有可用 BOM 复用；2 个 BOM 的头创建与审核均晚于订单审核日 1 天；另外 8 个未找到 BOM。两个 1 天样本没有订单级 ECN/研发需求关联，故只是日期差观察值，不能作为“订单导致的新 BOM 编制周期”指标。排除复用项后只有 2 个未归因样本：均值、中位数、最小值和最大值都是 1 天，但统计样本不足且因果关系未证实，不建议作为业务 KPI。
- BOM 子件可按 `BOM_D.SOURCE_ID_ROid → ITEM.ITEM_BUSINESS_ID` 遍历；全表值域核查 995,460 / 995,467 行能匹配到品项。能做多阶结构扫描，但“哪些物料必须有下阶 BOM”需由物料属性、采购/外协规则和业务例外共同决定，不能把每个子件都设为必有 BOM。
- 历史结构恢复能力不完整：`HISTORY_BOM_D` 当前 0 行；有 22,453 条 `ECN_D`、36,202 条 `ECN_SD`，其中当前 BOM 头仅 14,563 / 287,644 通过 `BOM_CHANGE_D_ID` 指向 ECN 明细，其他 273,081 条该引用为零 GUID。工程变更可为部分记录提供时间线，但不足以证明所有 BOM 的历史完整结构。

## 1. 数据源与安全方式

通过项目已有 `data-operations/e10/pmc_rd_progress_probe.py` 的 `E10Repository` 只读适配器连接，复用 `/data/automation/code/work/basci/basic_code` 的 `MSSQLDatabase` 配置，没有输出或复制凭据。适配器使用 SQL Server 只读连接，设置 `READ COMMITTED` 和 10 秒锁等待。本次首条查询实测 `DB_NAME()` 为 `E10_6.0.0.1.NEW.CHS`，来源与当前任务的 E10 一致。

项目中另有 `pmc_rd_progress_reader.py`，也是订单行与 BOM 事实读取入口；现有 `pmc_rd_progress_probe.py` 已明确不将 `BOM_D.OPERATION_ID` 或工单工序物料关系当作 BOM 完成规则。本次只使用其订单、品项、工厂物料和 BOM 查询能力。

工作区原有其他任务的未提交修改较多。本次未修改它们；只新增本报告和 SQL 文件。初次元数据探查有一个不存在的候选表名，查询失败后按 `sys.tables` 校正；全程只读，没有生产数据变更。

## 2. 实测表结构和关联

| 业务关系 | 实际键与字段 | 结果及边界 |
|---|---|---|
| 订单头 → 订单明细 | `SALES_ORDER_DOC.SALES_ORDER_DOC_ID = SALES_ORDER_DOC_D.SALES_ORDER_DOC_ID` | 实测 SQL 与现有读取器一致。订单号显示字段为 `DOC_NO`；订单日期为 `ORDER_DATE`。 |
| 订单明细 → 品项 | `SALES_ORDER_DOC_D.ITEM_ID = ITEM.ITEM_BUSINESS_ID` | `ITEM_CODE` 是业务显示/匹配码，稳定关联应使用 UUID；明细另有 `ITEM_FEATURE_ID`。 |
| 品项 → 事业部/工厂物料属性 | `ITEM_PLANT.ITEM_ID = ITEM.ITEM_BUSINESS_ID` | 读取 `Owner_Org_ROid`、`ITEM_PROPERTY`、`ITEM_ROUTING_CONTROL`、`STANDARD_ROUTING_ID`。样本中每个品项按适用工厂行解析；正式使用应拒绝多行歧义。 |
| 品项/组织 → BOM 头 | `BOM.ITEM_ID = ITEM.ITEM_BUSINESS_ID` 且 `BOM.Owner_Org_ROid = ITEM_PLANT.Owner_Org_ROid` | 现有项目探查器使用这一组织范围。不能只按订单号连接 BOM，也不能只按品项编码跨组织取版本。 |
| BOM 头 → BOM 子件 | `BOM_D.BOM_ID = BOM.BOM_ID` | 子件源项字段为 `BOM_D.SOURCE_ID_RTK` / `SOURCE_ID_ROid`；当来源为 ITEM 时，后者与 `ITEM.ITEM_BUSINESS_ID` 值域匹配。全量 995,467 条 BOM_D 中 995,460 条匹配，7 条未匹配，应作为异常/待确认，不能静默丢弃。 |
| BOM 子件 → 下阶 BOM | `BOM_D.SOURCE_ID_ROid → ITEM → ITEM_PLANT → BOM(ITEM_ID, Owner_Org_ROid)` | 可按需递归。是否必须展开由子件的物料属性和供应/工艺规则决定；采购终端件不应被要求存在下阶 BOM。 |
| BOM 变更 | `BOM.BOM_CHANGE_D_ID → ECN_D.ECN_D_ID → ECN.ECN_ID`；`ECN_SD.ECN_D_ID` 关联 ECN BOM 子件变更 | 该路径只对有非零变更引用的 BOM 头有效，当前覆盖 14,563 个头；不能代表全体历史。 |

**订单专用/客户专用 BOM：**核心 `BOM`、`BOM_D` 字段中没有销售订单 ID 或客户 ID。`SALES_ORDER_DOC_D` 有 `ITEM_FEATURE_ID`，但现有项目先前对 E10 订单样本核验显示为零 GUID；本轮已选样本也未以非零特征作为版本区分依据。E10 另有 `BOM_AUTO_CONFIG*`、`BOM_MANUAL_CONFIG*`、`BOM_PRODUCT` 等配置/联产品表；本次实测自动/手工配置主表及明细表为 0 行，`BOM_PRODUCT` 为 287,644 行，但没有发现其与销售订单头/行的直接关联。因此目前能验证的优先键是品项 + 工厂组织（如将来出现非零特征，须将特征纳入适用性解析）；没有证据可按客户或订单选 BOM。

**版本数量：**`BOM.VERSION_TIMES` 存在，样本可见 `0000`、`0003` 等值；当前全表按 `(ITEM_ID, Owner_Org_ROid)` 分组，重复 BOM 头组数为 0。也就是说当前表以单个当前头为主，不能把它解释成保留了每一历史版本的多行版本库。抽样范围内候选池 300 条品项均至多关联一个同组织 BOM 头；无真实“同品项同组织多个当前 BOM 版本”样本。

## 3. 日期字段、审核及历史可信度

### 订单时间

- `SALES_ORDER_DOC.ORDER_DATE`：业务日期，样本为日期粒度；不能默认代表审核/实际下达时刻。
- `SALES_ORDER_DOC.CreateDate`：订单头写入 E10 的创建时间。
- `SALES_ORDER_DOC.LastModifiedDate`：最后修改时间，不等于审核或下达。
- `SALES_ORDER_DOC.ApproveStatus` / `ApproveDate` / `ApproveBy`：审核状态、审核时间和审核人。样本筛选使用 `ApproveStatus='Y'`。若公司“订单下达”指 E10 正式审核，建议以头部 `ApproveDate` 为基准；需要业务确认。
- 订单明细 `SALES_ORDER_DOC_D` 也有创建、修改、审核字段。订单最终是否下达仍以头部批准为统一口径，并可将明细审核异常单列。

### BOM 时间

- `BOM.CreateDate`：当前 BOM 头行创建时间，适合作为记录首次创建代理值；若 BOM 头被复用更新，不等于当前结构创建完成。
- `BOM_D.CreateDate`：当前子件行记录创建时间。最大明细创建时间可用于排查，但不证明当时已达到完整结构。
- `BOM.LastModifiedDate` / `BOM_D.LastModifiedDate`：最后一次修改时间，不能直接用作完成日。
- `BOM.ApproveStatus`、`ApproveDate`、`ApproveBy`：本次当前数据中状态 Y 的 287,599 个 BOM 头审核日期均非 1900 哨兵且审核人非零；N 的 31 个头均为 1900 日期/零审核人；V 的 14 个头有既往审核时间。状态值实际为 Y/N/V；N 表示未审核可由数据佐证，V 的正式中文状态名仍建议由 E10 管理员确认。
- `BOM_D` 也有审核字段，但当前 995,369 条 Y 明细中有 18,642 条 `ApproveDate=1900-01-01` 且 `ApproveBy=零 GUID`。因此明细审核日期不适合直接作为结构最后批准时刻；优先用 BOM 头审核时间，并结合明细 `ApproveStatus`、`EFFECTIVE_DATE`、数据库拼写为 `EXPRITY_DATE` 的失效日期判断在指定时点是否有效。
- `HISTORY_BOM_D` 实际 0 行。`ECN` 16,121、`ECN_D` 22,453、`ECN_SD` 36,202、`ECN_SSD` 0、`ECN_BOM_SD` 0 行。`ECN_SD.BOM_SEQ_ID` 与当前 `BOM_D_ID` 有 36,201 / 36,202 行值域匹配，显示部分变更可追踪；但这不是每个 BOM 的完整历史快照。
- `BOM.BOM_CHANGE_D_ID` 非零并匹配 ECN_D 的 14,563 个；其余 273,081 个为零 GUID。即使 ECN 记录存在，也不能据此补出未记录的旧结构。

**可准确计算 / 估算 / 无法计算：**当前 `CreateDate` 与头 `ApproveDate` 对当前行可读；订单和 BOM 头审核的日期差可计算。当前结构的首个“完整”时间原则上只能估算为 BOM 头批准且结构有效的日期。对历史时点的完整结构，只有存在连续 ECN 变更证据的个别 BOM 可以尝试重建；普遍样本不能准确还原。不能从今天的 BOM 当前状态倒推历史上已完整。

## 4. BOM 完整性判断规则

### 可由系统自动检查的部分

1. **是否需要 BOM**：复用当前 E10 探查器已落实的组合规则。`ITEM_PROPERTY=P` 且 `ITEM_ROUTING_CONTROL=0` 标记为不适用；`M` 且控制值 `1/2` 属于需研发候选。其他属性/控制组合必须保留为待业务确认，不能套用二元规则。`2` 的特征路线还有独立验证缺口，不影响 BOM 子件可解析性。
2. **母件匹配**：订单明细 ITEM UUID → ITEM 主数据 UUID → ITEM_PLANT 适用组织 → BOM ITEM UUID + Owner Org；若配置特征非零，再按 E10 确认的特征适用规则匹配。
3. **BOM 头状态**：只有 `ApproveStatus='Y'` 才符合已审核候选；N/V 不能作为当前有效 BOM。多候选时必须依 E10 生效、组织和版本规则唯一选定；当前 E10 同一 ITEM/组织不存重复 BOM 头。
4. **子件关系**：`BOM_D.BOM_ID` 归属母 BOM；`SOURCE_ID_ROid` 连接 ITEM。可核对子件是否存在、用量 `QTY_PER` 与 `DENOMINATOR` 是否正值、明细是否 Y、有效期区间是否覆盖统计时点、是否存在源项不匹配。
5. **多阶展开**：仅对业务规则确认必须自制展开的子件继续追踪其同组织有效 BOM；采购/外购件通常终止。递归要维护路径集合，检测环路，设置最大深度并输出超深/循环异常，不能无限展开。

样本 `WFV175D01-1/1` 的当前 BOM 有 8 条有效已审核子件，8 个子件 UUID 均能找到 ITEM；数量/分母均正。按 `ITEM_PLANT` 目前可见 6 个 M 类子件、2 个 P/控制 0 子件；6 个 M 子件中仅 1 个当前可找到下阶 BOM。该事实能说明递归检查有意义，但“其余 5 个 M 类子件是否允许作为无下阶的自制终端件”仍需工艺/研发规则确认，不能直接认定 BOM 不完整。

### 系统检查不能证明的部分

- 是否遗漏了图纸要求、客户特定选件、法规件或未维护进 E10 的零件。
- 采购、外协、自制半成品、模块/组件何时必须继续展开，及允许无 BOM 的业务例外。
- 单纯结构有效不等于能投产、库存可供或业务上无缺料。
- 需要 E10 BOM 管理员/研发提供批准清单、配置规则或标准图纸/BOM 对照，才可验证业务完整性。

## 5. 订单 BOM 耗时规则建议

| 指标 | 建议算法 | 当前历史可计算性 |
|---|---|---|
| 首次创建耗时 | `BOM.CreateDate` 的日期 − 订单正式下达日期（建议头 `ApproveDate`）；只对归因到订单新需求的 BOM 计算 | 当前头创建日期可读，但无法证明创建由该订单引起；订单前已存在的 BOM 标为复用并置准备等待 0 天，不纳入编制周期。 |
| 结构完成耗时 | 首次保存的结构快照满足：所有必需子件存在、用量有效、该展开终点规则满足、无循环，日期 − 下达日期 | 当前不能普遍还原首次满足时点。`LastModifiedDate` 或“最后一行 CreateDate”不得替代。 |
| 正式可用耗时 | 首次达到结构完整，且 BOM 头已审核、适用版本已生效、所需明细有效的日期 − 下达日期 | 当前仅当前头审核/有效状态可判。历史完整状态缺快照，不能普遍准确计算。 |

按自然日计算，同日为 0。订单下达前已有且当时有效的 BOM：标“已有 BOM 复用”，等待 0、排除新建周期。订单后创建或变更的 BOM，必须有订单/ECN/研发任务关联，或经业务人员明确归属，才计入该订单周期；仅凭 BOM 时间比订单晚不够。

多品项订单逐品项判断；无需 BOM 的品项标“不适用”。整体完成时点取所有必需品项 BOM 正式可用日期最大值；任一必需品项未完成则订单整体未完成。若订单后修改 BOM，要记录关联变更原因，不能把无关产品维护周期并入订单。

## 7. 后续 KDOS 功能设计

建议入口：**PMC 中心 → 报表 → 订单 BOM 完成进度与耗时分析**。第一版应展示“数据能证明的状态”，把无法还原的历史时点明确标为不可计算，而不是回填估计日期。

### 页面指标与明细

- 订单品项明细：订单号/行、品项编码/名称、事业部或 E10 组织归属来源、订单业务日期、订单创建/审核日期、是否需 BOM、适用 BOM 头/版本、BOM 创建/审核/生效状态、当前结构层级、最后同步时间及来源时间。
- 未完成明细：必需但无 BOM、BOM 未审核/失效、明细无效/过期、子件引用失效、数量无效、下阶必需 BOM 缺失、循环、多个适用候选或组织/特征歧义。正常不适用的采购品不计入异常。
- 统计：适用订单品项数、已有 BOM 复用数、未建数、当前未审核/无效数、可计算周期样本数；事业部完成率与平均/中位耗时按归属规则明确显示覆盖率。不能把没有归因的 E10 BOM 时间纳入订单研发周期。
- 趋势：按订单审核月份统计已完成和未完成订单品项，另按新 BOM 归因事件计算周期分布；复用 BOM 单独统计，不混入编制时长。
- 结构异常：按 BOM 头/子件路径显示缺失 ITEM、非正用量、有效期不重叠、下阶缺项、环路/深度超限。此项表示系统结构异常，不等价于已证明业务缺料。

### 数据采集与历史方案

- E10 当前可读订单头/明细、ITEM、ITEM_PLANT、BOM/BOM_D、ECN/ECN_D/ECN_SD 及时间、审批状态和有效期字段；继续通过 Integration Adapter 只读获取，不让 Planning 直接连接 ERP。
- KDOS 可定期同步稳定的订单行、适用 BOM 头及全层子件快照。字段至少保留来源库、源主键、订单行 UUID、ITEM UUID、组织 UUID、BOM ID/版本、状态、有效区间、父子组件 UUID、数量、源创建/审核/变更时间和抓取时间。未经确认的历史关系不回填。
- 对未来首次完整时刻，优先消费/轮询 E10 ECN 审核事件并保存变更前后 BOM 完整快照；若 E10 无可靠事件接口，按小时或每日保存版本快照只能把时间定位到两个采样点之间，精度标为区间，不宣称精确时刻。对高时效 KPI 应采用 ECN 完成事件加事务后快照。
- 同一 `ITEM UUID + 组织 + 特征/配置 + BOM 适用版本` 的已有有效 BOM 对多个订单复用时，存 BOM 版本状态并为每个订单行产生“复用、0等待”；只有经 ECN/研发任务或人工确认的需求关联才产生新编制周期。
- `BOM_D.OPERATION_ID` 当前全零或未能建立工序归属时，不将工艺路线/BOM 工序匹配当作设计 BOM 完成门槛；工序研发进度应作为独立指标。

### 需业务人员确认

1. “订单下达”是否以销售订单头审核 `ApproveDate` 为准，还是以 `ORDER_DATE`、合同生效或另一业务事件为准？
2. 哪些 `ITEM_PROPERTY`、`ITEM_TYPE`、`ITEM_CATEGORY`、`SOURCE_TYPE` 组合表示采购、外协终端、自制需继续展开？M 类子件无 BOM 是否允许特例？
3. 非零订单特征码、客户配置、订单专用 BOM 的正式选择顺序是什么？现有样本未验证到有效特征差异。
4. BOM 的“正式可用”应以头审核时间、明细有效起日、ECN批准时间还是三者共同判定？状态 V 的正式含义是什么？
5. 哪类 ECN/研发任务可证明变更由某个销售订单引起？没有这个业务引用时如何归因？
6. 事业部按 KDOS 订单分配、E10 销售部门、`Owner_Dept` 或工厂来源哪个确定？`Owner_Dept` 不能未经验证等同 KDOS 事业部。

## 8. 验证记录和限制

- 已实测：E10 数据库名、核心表/列、订单行→ITEM→ITEM_PLANT→BOM/BOM_D UUID 关系、BOM状态与审核日期质量、ECN关联覆盖、30条订单品项样本和样本当前可用状态。
- 样本 SQL 使用受控最近审核订单范围；此报告不保存客户资料、完整行快照或密钥。
- 未对完整 BOM 树逐个递归展开数十万 BOM；已对一个 8 子件的真实样本验证首层子件 UUID、数量和下阶候选，递归规则需按确认的物料/供应分类执行。
- 未能把 2 条订单后 BOM 建档与订单研发工作建立因果关联；不报告为已证实新建周期。
- 未开发 KDOS 页面或同步作业；没有生成定时任务、写 E10/KDOS、跑迁移、部署、提交或推送。
- 工程变更链有局部证据，但 `HISTORY_BOM_D` 为空且多数 BOM 头没有 ECN 明确关联，因此历史结构完成时间总体无法恢复。

## 最终建议

后续报表应把“当前 BOM 结构/审核完整性”和“订单归因的 BOM 编制周期”分成两类指标。第一类可由 E10 当前表结构按已确认规则部分自动判断；第二类必须先有可追踪的订单-研发/ECN关联和持续历史快照。对订单前有效 BOM 记为复用、等待 0 且排除编制周期；对缺少归因证据的订单后 BOM 只显示时间先后，不计入周期统计。
