# E10 与 T+ 订单数据源只读测试报告

- 测试时间：2026-08-31（Asia/Shanghai）
- 测试范围：鼎捷 E10、用友 T+ 两套账套，完全独立连接和查询
- 测试方式：只读 SQL、系统目录、会话级统计、内存内样本比对
- 变更声明：未修改 KDOS 项目代码，未修改 E10/T+ 数据库，未创建索引，未启用 CDC/Change Tracking，未落盘业务快照，未改变网络通道

## 一、执行摘要

1. E10 与 T+ 均可连接，当前账号都是 `db_datareader`，不是 `sysadmin`、`db_owner` 或 `db_datawriter`。
2. E10 通过私网地址直连 SQL Server 1433；T+ 继续通过本机 `127.0.0.1:14330` 的 Cloudflare Access TCP 通道访问，没有开放数据库公网端口。
3. E10 和 T+ 的订单结构、修改时间、主键、状态和库存事实完全不同，不能共用 SQL，也不能共用游标。
4. 当前可立即实施的方案都是“按修改时间 + 主键”增量，但必须分别读取主表和明细表；只读主表会漏掉 E10 的 273 条、T+ 凯南账套的 4,747 条、T+ 科加账套的 12,025 条“明细修改时间晚于主表”的历史明细。
5. E10 数据库已启用 Change Tracking，自动清理、保留 1 天，但订单明细表未启用，且当前账号没有 `VIEW CHANGE TRACKING`，所以当前不能作为完整订单同步方案。T+ 两个账套均未启用 Change Tracking 或 CDC。
6. 三个数据库均未启用 CDC。本次没有自行启用，也没有做虚假的 CDC 性能测试。
7. 2026-01-01 至测试日样本包括 E10 7,373 单/39,285 行，T+ 1,437 单/13,947 行。发现 9 个完全同号、312 个“去除 E10 组织前缀后同号”、99 个“T+ 号包含 E10 号”和 27 个“E10 号包含 T+ 号”的候选关系。既存在高度可信的同一业务订单，也存在同号但内容不同的情况，直接按订单号合并会重复或误合并。
8. 最终计划中心应保留 E10、T+ 两边原始记录，在其上建立独立的“业务订单归并层”。不能把两个源直接相加，也不能全局指定一个系统覆盖另一个系统。

### 如由 DBA 后续完善 Change Tracking

1. 在备份/克隆环境先确认 ERP 厂商支持和升级影响。
2. E10 将保留期由 1 天评估提升至至少 7–14 天；T+ 如启用，两个账套分别配置。
3. 对订单头、订单明细、交付计划，以及大屏实际需要的出库/库存表逐表启用，不能只启用主表。
4. 给专用同步账号授予目标表主键和业务列 `SELECT`、表级 `VIEW CHANGE TRACKING`；不授予写权限。
5. 做一次一致性全量初始化并保存每库版本；每次续传先比较 `CHANGE_TRACKING_MIN_VALID_VERSION`。
6. 监控内部表增长、自动清理、最旧未消费版本和同步延迟。CT 保存主键与变化元数据，存储量通常低于 CDC，但仍有写放大和内部表空间成本。

### 如由 DBA 后续评估 CDC

1. 当前三个库均未启用，故本次无 CDC 吞吐/延迟实测。
2. SQL Server 上启用数据库级 CDC 需要 `sysadmin`；数据库启用后，`db_owner` 可为单表建立 capture instance。微软官方说明：<https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/enable-and-disable-change-data-capture-sql-server>。
3. 启用前确认 SQL Server Agent、恢复模式、日志备份、独立文件组/容量、清理任务、保留期、监控告警和 ERP 厂商支持。
4. CDC 会保存变更行及元数据，能识别插入、更新、删除，但增加日志读取、存储、清理和运维复杂度。空间应按“日变化行数 × 捕获列宽 × 保留天数 × 更新前后镜像/索引系数”在测试库实测，不在未启用状态下编造数值。
5. 两个 T+ 账套必须分别启用、分别建 capture instance、分别保存 LSN 游标，不能用一次跨库 CDC 查询。

| `S-2604117` | `A012-S-2604117` | 否 | 是 | 是（40） | 是，但发生拆并 | 行数 20 vs 10；禁止用行号一一硬配，按源行 ID + 品号/数量建立映射 |

### 判断

1. 两边确实存在相同业务订单，而且复制方向不是单向固定的：有些 T+ 号进入 E10 后增加 `2301-` 等组织前缀；有些 T+ 号反而包含 E10 的 `S-...` 号。
2. 订单号相同不保证内容相同；同一业务订单也可能因为组织、拆单、合单、客户主体或交付计划转换而号码不同、行数不同。
3. 无法把一个系统全局定义为所有订单的唯一主来源。主来源必须按订单血缘判断：
   - E10 为 `23xx-<T+号>` 且 T+ 更早时，T+ 是该业务订单的起点；
   - T+ 号包含 E10 `S-...` 且业务内容一致时，E10 是该业务订单的起点；
   - 同号但内容不一致时先保持两单，等待规则或人工确认。
4. 两边原始记录必须保留。原始唯一键使用 `(source_system, source_database, source_order_id)`；另建 `business_order_id` 归并层和来源映射表。
5. 订单事实也不能全局二选一：E10 的 `SALES_ISSUE`/库存事实对 E10 执行链权威；T+ 的 `ST_RDRecord`/现存量对各自账套权威。大屏汇总时按业务订单血缘选择事实来源，不能把两边同一执行事实相加。

## 八、最终建议

### 1. E10

- 当前采用方案 A：对 `SALES_ORDER_DOC`、`SALES_ORDER_DOC_D`、`SALES_ORDER_DOC_SD` 分表执行 `LastModifiedDate + 主键` 增量；若展示出库/库存，再为 `SALES_ISSUE`、`SALES_ISSUE_D`、`ITEM_WAREHOUSE` 建各自游标。
- 目标方案是完善后的方案 B：由 DBA 将 CT 覆盖到所有需要的明细表、把保留期提高到至少 7–14 天并授予只读同步账号 `VIEW CHANGE TRACKING`。在此之前不能将现有 CT 称为可用订单方案。
- 建议频率：2 分钟；每表单批最多 1,000 行。
- 游标：`source_database + table_name + LastModifiedDate + PK(UUID)`；查询条件使用 `time > @time OR (time = @time AND pk > @pk)`，按二者排序。
- 每日低峰做活动订单全量校验，每周做较长时间窗全量对账，用于发现硬删除和修复游标遗漏。

### 2. T+

- 当前采用方案 A，但凯南智能、科加智能必须是两个独立账套任务；每个任务再为 `SA_SaleOrder`、`SA_SaleOrder_b`、需要的 `ST_RDRecord`/库存表分别保存游标。
- `SA_SaleOrderChange`/`_b` 作为变更审计补充，最终事实仍回读正式订单表。
- 建议频率：每个账套 5 分钟；单表单批最多 500 行。使用最多 2 个长连接的小连接池，不要每批重新建立 Cloudflare 通道连接。
- 游标：`source_database + table_name + updated + ID`；两个账套的游标、日志和重试状态绝不能共用。
- 每日低峰做活动订单全量校验；在 CT 未启用前，这是识别硬删除的必要补偿。

### 3. 两个数据源是否使用同一种方案

- 当前都可以使用方案 A，但只能复用同步框架，不能复用 SQL、字段映射、状态枚举、游标值或删除规则。
- 中期不必强求同一种方案：E10 更接近完善 CT 的条件；T+ 可继续方案 A，待 DBA/厂商评估后再决定 CT。

### 4. 任务、日志与重试

至少建立三个顶层任务：`E10`、`T+ 凯南智能`、`T+ 科加智能`。每个任务拥有独立的连接配置、表级游标、同步日志、错误日志、失败重试记录和最近同步时间。

失败策略：

1. 只有目标端整批幂等提交成功后才推进游标。
2. 以 `(source_system, source_database, source_table, source_pk)` 幂等 upsert。
3. 重试建议 1、2、5、10、30 分钟并加随机抖动；达到上限后保留错误和批次边界，不跳过游标。
4. T+ 网络错误优先复用/重建连接，不把一个账套失败扩散到另一个账套。
5. 使用 2–5 分钟重叠窗口重复读取，目标端依靠幂等键去重。
6. CT 将来启用后，每次先校验最小有效版本；版本过期立即停止增量并触发全量重建，不能从错误位置继续。

### 5. 删除、作废和关闭

- 不物理删除计划中心的源订单，保留原始状态和审计历史。
- E10 将 `ApproveStatus`、订单头/交付计划 `CLOSE` 映射为独立规范状态；T+ 将 `voucherState`、`isCancel`、`CloseDate/Closer`、行关闭字段分别映射。
- 作废/关闭是状态更新，继续显示或移入历史视图；未完成量、活动订单数等指标按规范状态过滤。
- 方案 A 看不到源库硬删除。仅在连续两次全量对账均缺失并经过宽限期后标记 `SOURCE_MISSING`，不要立即删除；完整 CT/CDC 启用后才消费真实删除事件。

### 6. 最终计划中心来源

最终应以 E10 + T+ 共同作为订单来源，但采用“两层模型”而不是简单合并：

1. 原始层：三套独立来源记录完整保留，不互相覆盖。
2. 业务订单层：通过显式映射、号码变换规则、多字段指纹和人工复核生成唯一 `business_order_id`；大屏每个业务订单只计一次。

在映射规则上线前，大屏应默认按来源分栏或显示“疑似重复”标记，禁止直接对 E10 与 T+ 订单数量/金额求和。
