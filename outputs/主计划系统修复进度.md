## 当前任务 KN-TEST-001（已完成）：修复 Web 全量测试 teardown 异步泄漏，使 @tracker/web 全量 Vitest exit code = 0

### 原现象

`pnpm --filter @tracker/web test` 断言全部通过（22 files / 119 tests），但 Vitest 进程收尾时偶发 `Errors 1~2` 且 exit code = 1：

```
ReferenceError: window is not defined
 ❯ react-dom-client.development.js:17920
 ❯ Immediate.performWorkUntilDeadline (scheduler.development.js:45)
 ❯ processImmediate (node:internal/timers)
This error originated in "src/modules/portal/ModulePortal.spec.tsx" test file.
```

- 复现：单文件 `ModulePortal.spec.tsx` 连续运行一直 exit 0（8/8 干净），**只有全量 suite 才复现**；未修复前全量连续运行多次中约 1/3 出现该错误（exit 1）。

### 真实根因

- react-dom `:17920` 就是 React 被动副作用 flush 回调里的 `schedulerEvent = window.event;`——即 **React 通过 `setImmediate` 调度的 passive-effects flush 在 jsdom 环境销毁之后才执行**，读到 `window` 报错。
- 触发源：`ModulePortal.spec.tsx` 最后一项“保存模块顺序”测试调用真实 `App.useApp().message.success("模块顺序已保存")`，AntD 通知挂载 + rc-motion 动画会产生**在 act/await 窗口之外**的一次提交，其 passive-effect flush 被排进宏任务；同时当前 `cleanup()` 写在 `beforeEach`，**最后一个测试的 React 树从未被卸载**，于是这份待执行工作一直留到 teardown。
- 因此这是 **jsdom 测试生命周期问题**，生产浏览器不存在该泄漏（生产代码未发现卸载后 setState / 未取消 timer / 未取消订阅）。按任务边界：修测试，不改 `<AntApp>` 的正式用法，不删生产 message 功能。

### 修复方式（仅测试）

1. `apps/web/src/modules/portal/ModulePortal.spec.tsx`
   - `cleanup()` 从 `beforeEach` 移到正式 `afterEach`：每个测试（含最后一个）结束时都卸载 React 树，让待执行的 passive-effects flush 随卸载被丢弃。
   - 用 `vi.hoisted` + `vi.mock("antd")` 稳定替换 `App.useApp()` 的 `message`（及 notification/modal 桩）：测试只验证 ModulePortal 业务行为，不再运行动画生命周期；新增断言 `message.success` 被调用 1 次，保留“保存成功会提示”的业务语义。
   - 最后一个测试在保存后**等待组件真正 settled**：等待退出排序态（“调整顺序”重新出现、“保存顺序”消失），再断言 API 调用与 localStorage。
2. `apps/web/src/test-setup.ts`
   - 用 Testing Library 正式配置 `configure({ asyncUtilTimeout: 5_000 })`：全量并行运行时 CPU 竞争会让默认 1s 的 `waitFor/findBy` 偶发超时（另有一个与 teardown 无关的既有负载敏感 flake：`MasterPlanPages.spec.tsx` “连续 blur 保存”默认 1s 超时）。断言本身不变，真实错误仍会失败，只是不再因机器瞬时负载随机报红。

均属测试隔离/生命周期修复，**不是** ignore / skip / `|| true` / `process.exit(0)` / 全局 fake timers / sleep 等隐藏手段。

### 根因审计（KN-MPS-SYNC-001 根因审计）

1. **主投影 upsert 的 eligibility**：`baseToWeekly()` 的 `INSERT INTO mps_weekly_plans … FROM mps_base_plans base … WHERE base.tenant_id=$1 AND ${weeklyAdmissionSql(base,'base')}` —— 只处理满足准入（`latest_review_due_date` / `product_attribute` / `surface_nature` / `manufacturing_method` 非空）的基础计划。
2. **原 ensureExecutionRows 的 weekly 查询范围**：紧随其后的 `SELECT w.*,c.… FROM mps_weekly_plans w LEFT JOIN mps_process_cycles c … WHERE w.tenant_id=$1` —— **只按 tenant 全表扫描**，无 base 关联、无 admission。
3. **两者是否一致**：否。前半段受准入控制，后半段越界。
4. **为什么越界处理历史 weekly**：历史/初始化 weekly 的 base 评审交期为空 → 不满足准入；旧执行范围按 tenant 全表把它们全部送入 `ensureExecutionRows`；其 `manufacturing_method=NULL` 又把 `mps_weekly_process_plans.execution_enabled` 冲成 false 并生成技术/主材占位（KN-MPS-INIT-001 前的真实故障来源）。

### 修复（scope）

- 执行范围改为：`FROM mps_weekly_plans w JOIN mps_base_plans base ON base.tenant_id=w.tenant_id AND base.id=w.base_plan_id LEFT JOIN mps_process_cycles c … WHERE w.tenant_id=$1 AND ${admission}`。
- **复用同一份 `weeklyAdmissionSql(basePlan,'base')`**，未手写第二套准入条件；**未用 RETURNING-only**（工序周期变化时 admitted weekly 仍按最新 cycle 重算）；`ensureExecutionRows` 业务规则与历史 weekly 生命周期一律不动。

## 当前任务 KN-FILTER-003（已完成）：高级筛选 datetime 时间精度与时区语义修复

最后更新时间：2026-09-17（Asia/Shanghai）。任务关键字 `KN-FILTER-003`。开始 HEAD `d1313e1`。

### 问题与根因

- 现象：高级筛选选择 datetime 字段时，无论选几点几分，选择完成后都退回 `00:00:00`。
- **前端根因**：`apps/web/src/shared/advanced-filter.tsx` 的单值分支与 between 分支都用 `<DatePicker showTime>`，但提交时统一 `next.format("YYYY-MM-DD")` → `2026-09-17 15:36:25` 被序列化成 `2026-09-17`，回显 `dayjs("2026-09-17")` 自然是 `00:00:00`。
- **后端根因**：`apps/api/src/common/filtering/sql-filter.compiler.ts` 的 `dateOperand()` 末尾 `text.slice(0, 10)`，date/datetime 共用该操作数且共用 `::date` 自然日区间比较 → 即使前端提交完整时间也被截断并按整天比较。
- 影响范围：平台级（所有正式 resource 的 datetime 字段，含 `createdAt`/`updatedAt`/`startedAt`/`importedAt`/`lastLoginAt` 等），不只是主计划页面；打印/导出继承同一 applied `FilterGroup`，因此同样受影响。

### 数据库时间语义审计（修复前执行）

- 应用库 `four_department_tracker`：`timestamp with time zone` **171 列**，`timestamp without time zone` **0 列**。
- KDOS 库 `kdos`：`timestamp with time zone` **56 列**，`timestamp without time zone` **0 列**。
- 结论：全部正式 datetime 字段都是 `timestamptz`（绝对时间点）。用户输入是 **Asia/Shanghai 墙上时间**，必须带显式 `+08:00` 转换成绝对时间后比较；实测连接会话 `TimeZone = Etc/UTC`，因此**不能**依赖会话时区。

### 前端修复

1. 新增正式 temporal serializer：`FILTER_DATE_FORMAT = "YYYY-MM-DD"`、`FILTER_DATETIME_FORMAT = "YYYY-MM-DD HH:mm:ss"`、`serializeTemporalFilterValue(field, value)`（按 `field.type` 分流），禁止 datetime 走 `YYYY-MM-DD`。
2. 新增 `TemporalInput`：`date` 用普通 DatePicker（`format="YYYY-MM-DD"`）；`datetime` 用 `showTime={{ format: "HH:mm:ss" }}` + `format="YYYY-MM-DD HH:mm:ss"`，单值与 between 的 min/max 共用同一实现（回显用 `dayjs(String(value))`，完整保留时分秒）。
3. 不做 `toISOString()` 隐式偏移，不依赖浏览器本地时区；draft/applied/URL/JSON 全链路只搬运字符串，实测往返不截断。

### 后端修复

1. `dateOperand()` 与 `datetimeOperand()` 正式拆分：date 仍只接受/规范 `YYYY-MM-DD`（保持既有自然日语义不变）；datetime 接受 `YYYY-MM-DD HH:mm[:ss[.SSS]]` 或 `T` 分隔形式，规范化为 `YYYY-MM-DD HH:mm:ss[.SSS]` 并追加业务偏移 `+08:00`，**绝不 slice(0,10)**。

## 当前任务 KN-MPS-EXEC-001（第二轮收口·已完成）：月计划生产进度口径修正

最后更新时间：2026-09-17（Asia/Shanghai）。任务关键字 `KN-MPS-EXEC-001`（未创建新任务号）。

### 用户最终确认的业务口径

月计划生产进度 = **整个订单/月度总需求完成率**，不是“已下达周计划部分的执行完成率”。

- 周计划（不变）：`SUM(该 weekly + process 的全部实际报工) / weekly.planned_quantity`。
- 月计划（本轮修正）：`SUM(当前 monthly 所有关联 weekly 当前 process 的全部实际报工) / monthly.required_quantity`。
- **禁止**再用 `SUM(weekly.planned_quantity)`（已下达周计划数量）做月计划进度分母；它只能作为 Hover 辅助信息。
- 允许 >100%，不封顶；`required_quantity` 为 0/NULL → `—`。
- 状态与进度完全独立（不互相推导）：允许“状态：已完成 / 生产进度：60%”。

### 根因

第一轮实现的 `monthlyProcessDemand = SUM(weekly.planned_quantity)` 被当作月计划进度分母，等价于“已下达周计划部分的完成率”，会系统性高估月计划完成度（样例：`255/300=85%`，正确应为 `255/500=51%`）。

## 当前任务 KN-PRINT-001（已完成）：KDOS 全平台统一表格打印

任务名称：KDOS 全平台统一表格打印
当前状态：**已完成**（2026-09-17，含选中打印缺陷修复与真实浏览器 UAT 10/10 通过）。

### 缺陷根因（用户报告：勾选 1 条后打印预览仍是全部记录）

1. **前端根因**：`KdosDataTable` 同时存在两个打印入口——工具栏「打印筛选结果」调用 `runPrint()`（无 selectedIds，FILTERED）与选择工具栏「打印已选（N）」（SELECTED）；用户点顶部按钮就打印了全部筛选结果。
2. **前端次级根因**：用户管理、营销、数据中心等页面传入自定义 `rowSelection`，覆盖了平台内部选择状态，导致平台侧 `selectedRowKeys` 恒为空，「打印已选」读不到选择（等价于退化打印全部）。
3. **后端根因**：`TablePrintService.normalizeIds()` 用全局 UUID 正则过滤 ID，且用 `selectedIds.length > 0` 隐式推断模式——客户端 ID 一旦被过滤成空数组，就静默退化为 FILTERED 打印整表。另发现 SELECTED 的 count 分支丢失页面上下文（`query` 未传入）。

### 修复

1. **单一主打印入口**：工具栏只保留一个按钮，未选中显示「打印筛选结果」（FILTERED），有选中自动变为「打印已选（N）」（SELECTED）；删除 selection toolbar 里重复的打印按钮。
2. **选中优先强规则**：`rangeType` 由选择状态显式推导（SELECTED 优先），不再用 selectedIds 长度推断。
3. **显式协议**：`/table-prints/manifest` 与 `/table-prints/render` 都要求/接受 `rangeType`；`FILTERED` 一律忽略 selectedIds；`SELECTED` 的空/非法 ID → 400，绝不退化。
4. **resource 级稳定主键**：`TableFilterSource.recordKey = { field, type: uuid|text|integer|bigint }`（默认 uuid id），通用打印 SQL 按真实主键参数化查询与排序，不再假设 UUID。

### Root cause

重复发生在**投影分组阶段**，不在源数据主键阶段：去重/聚合身份与 `ON CONFLICT` 目标键不一致。

1. `order_items` 的 `summarized` CTE 把 `item_name`、`customer_code`、`customer_name`、`source_order_id` 一起放进 `GROUP BY`，而目标唯一键只有 (期间, 订单, 品项)。同一订单号/品项/月份下品名或客户字段不同的两条 ERP 行因此生成两组输入，却指向同一条 `order_items`，同一条 INSERT 内写同一目标两次 → PostgreSQL 直接报 `ON CONFLICT DO UPDATE command cannot affect row a second time`。
2. `orders` 的 `headers` 用 `DISTINCT ON(source_system,source_database,source_order_id)` 去重，而目标键是 `(source_database,order_number)`；同一订单号下多个 ERP 订单 ID 时同样会在一条 INSERT 内命中同一目标。

隔离复现（临时库，已删除）：相同两行输入用旧分组键（含 item_name）执行即报同一错误，用目标身份分组则成功合并为 1 行、数量 2。

### 业务合并规则（数据证明）

`order_items` 的正式身份是“租户内一张订单的一个品项每月一条记录”，生产既有数据中所有多行组（14/13/11/10/9/8/7/6 行）的 `production_quantity` 都等于对应 ERP 订单行数量之和，因此合并规则确定为：数量 `sum`、交期 `min`、品名/客户/来源订单 ID 取 `modified_at` 最新（同刻按 `source_id` 倒序）的一条；`sales_orders` 仍按 ERP 行主键逐行保留，不丢任何 ERP 行。
