# KDOS 主计划系统

本 Skill 是主计划业务行为的项目级入口。实现或调查计划生成、同步、生命周期、工序及报工时，先读本文件和 [事业部基础计划业务规范](../../../docskill/主计划/订单执行/事业部基础计划.md)。生产基线 `5f90e589f845defe2c02591072f0d285a3981e73` 固化了本 Skill 的周计划准入规则。

一般表格权限、租户、审计、API 和数据安全仍遵守 `.agents/skills/kdos-form-platform/SKILL.md`。涉及运行任务、outbox、调度或故障恢复时同时遵守 `.agents/skills/kdos-task-orchestration/SKILL.md` 和 `docs/operations/TASK_REGISTRY.md`。`docs/operations/MPS_UPSTREAM_DOWNSTREAM_LINKAGE_DESIGN.md` 含较早的调查和方案快照；遇到其中与本 Skill 冲突的 ACTIVE、来源确认或历史恢复门槛，以本 Skill 和现行 docskill 为准，不得从历史快照恢复旧准入规则。

## 计划层级与来源

| 计划/执行对象 | 直接数据来源 | 规则 |
| --- | --- | --- |
| 集团主计划 | 订单分配表 | 订单分配是需求依据。 |
| 事业部月度计划 | 订单分配表 | 订单分配的承接事业部决定归属；分配审核状态不构成额外准入门槛。 |
| 事业部基础计划 | 事业部月度计划 | 基础计划是事业部周计划的直接来源。出货计划不是基础计划生成前置来源。 |
| 事业部周计划 | 事业部基础计划 | 以基础计划当前有效业务数据和下述准入规则生成。 |
| 周计划工序明细 | 周计划及该事业部有效默认工序配置 | 使用事业部默认路线；不得用品项专属工艺路线替换该默认路线。 |
| 报工系统 | 有效周计划工序任务 | 待报工任务来自工序任务；实际报工记录只能由真实报工提交产生。 |

ERP 原始订单行 ID 和历史外键用于追溯时可以保留，但不作为周计划生成的必要关联条件。

## 周计划生成准入

事业部基础计划是周计划唯一直接业务来源。首次生成应以该基础计划的有效性、字段、数量、真实业务状态及工序配置判定。当前唯一的五项周计划必填字段由代码共享定义 `weeklyAdmissionRequiredFields` 提供：

1. 最迟客户交期 `latestCustomerDueDate`。
2. 最迟评审交期 `latestReviewDueDate`。
3. 产品属性 `productAttribute`。
4. 表面性质 `surfaceNature`。
5. 生产方式 `manufacturingMethod`。

空字符串与 `NULL` 都视为缺失。不得未经用户确认增加必填字段或准入限制。计划数量遵守现行数值规则及数据库约束；不得把 ERP 入库数量或报工数量当成计划数量。

业务/配置阻塞仅限真实情况：基础计划暂停、取消、失效或生命周期状态无效；真实对应月度业务需求暂停/取消；数量违反现行规则；需要内部工序但缺少该事业部有效默认工序路线；重复计划或与既有生产执行事实发生冲突。稳定父关系、租户/事业部归属、权限和审计规则继续有效。

`ACTIVE` 与 `LEGACY_RETAINED` 均可继续进行周计划生成判定。`LEGACY_RETAINED` 或来源待核实只代表历史追溯状态，不代表业务暂停或取消。历史月度来源没有关联、历史来源未确认、月度来源处于 `LEGACY_RETAINED`、缺少 ERP 原始订单行 ID、订单分配未审核、生命周期写入开关关闭、仅有 ERP 入库事实、或历史 outbox 为 SUCCESS/FAILED/BLOCKED/重试耗尽，都不得单独阻止首次周计划及安全的首次工序初始化。

不得通过隐藏的 Application 校验、SQL 谓词、生命周期守卫、触发器、恢复前置任务或间接来源核验重新引入上述限制。来源关联仍可用于追溯、审计及独立数据维护；来源恢复机制是否成功不能决定周计划准入。

## 自动同步、重试与幂等

- 使用现有业务事件、reconciliation/outbox、`base-to-weekly` 自动扫描和已登记的 30 分钟调度；不得新建重复定时任务。运行调度规则时同时阅读 `kdos-task-orchestration` 与任务台账。
- 事件、自动扫描和手工同步共用同一业务准入及生成服务。自动扫描必须主动发现当前符合条件但没有周计划的基础计划，不能只消费历史 outbox。
- 旧 outbox 的任何状态不能永久排除当前符合条件的计划。重新判断当前业务数据；可重试的当前失败要保留真实原因并按现有安全规则重试。
- 单条计划的真实阻塞或失败要被隔离并准确记录，不能回滚或跳过同一事业部/租户的其他有效计划。
- 一条基础计划最多一条有效周计划，一周计划＋工序编码最多一条工序任务。重复运行必须幂等，不覆盖实际报工、已锁定路线或其他执行事实。
- 周计划状态、缺少项和提示必须复用后端当前准入逻辑，准确区分字段缺失、缺少默认路线、等待自动同步、已进入周计划、真实业务阻塞和当前同步失败。不得再显示“基础计划历史来源待核实”作为生成阻塞。较旧失败仅作为审计留存，不得覆盖后续成功的当前状态。

## 工序与生产事实

- 新周计划按对应事业部已启用的有效默认工序配置初始化任务。没有有效默认配置时明确阻塞，不回退到通用十工序；工序标准顺序唯一来自 `@tracker/shared`。
- `自制` 生成内部工序任务；`自制+外协` 生成内部工序及外协执行任务；`中心外购`、`外协` 按现有规则不生成内部工序任务。
- 仅有 ERP 入库记录不是 KDOS 工序报工，也不阻止安全地生成缺失周计划或首次初始化工序任务。不得创建虚假/零数量报工来代替工序任务。
- 已有周计划、任务快照、锁定路线、报工、入库、审计及其他执行事实必须保留。普通修复不得重复生成、删除/覆盖事实、修改数量/事业部/默认路线，或为消除提示而重新激活真实暂停/取消计划。
- 首次补建工序只允许在该周计划此前没有任何工序快照、报工、持久路线锁或确认空路线审计时执行；不得覆盖已有或部分路线，不得重启人工停用任务。

## 故障排查和验收

涉及主计划生成时，沿完整链路分别检查实际业务行、事件与扫描入口、同步 outcome、周计划、工序任务和报工查询。不能仅凭页面标签、候选筛选、`outbox SUCCESS`、待处理数为零、ACTIVE 记录异常为零、自动任务成功、API 健康或单元测试宣布验收。全系统问题按所有受影响事业部独立扫描；保留单条隔离、批次上限、keyset/索引友好查询和合理 statement timeout，避免高成本全表相关查询拖垮 PostgreSQL。只用业务 Application Service 和既有同步机制修复，不直接插入派生业务数据。

回归必须覆盖以下场景；使用隔离数据库及真实自动同步入口，不能在生产创建合成业务数据：

1. 历史来源未确认、缺少历史月度外键、`LEGACY_RETAINED` 时，字段和业务条件齐全仍可自动生成。
2. 生命周期写入开关关闭及仅有 ERP 入库事实不阻止符合条件的首次生成/工序初始化。
3. 五项字段补齐后由自动扫描发现并生成，不需用户点击。
4. 自动同步、事件/outbox 和手工同步采用相同规则；历史 outbox 成功、失败或耗尽重试不永久阻塞。
5. 单条真实异常被隔离，其他有效记录继续；重复运行不产生重复周计划或工序任务。
6. 真实暂停、取消、无效状态、归属/重复计划冲突、路线缺失和执行保护仍有效。
7. 生成成功后读模型显示已进入周计划，旧错误不覆盖成功状态；缺路线/字段显示真实原因。
8. 所有需要内部工序的有效周计划均能在待报工 Query Service 查到应有任务；外购/外协按业务类型不误造工序任务。

历史故障仅作为回归数据参考，不得在代码或规则中硬编码订单/品号：`2025A027058 / TGH121HT-1/1`、`2026C369005`、`2301-2026A012101 / UMPI512-01-100-1/1`、`2301-2026C406004-3`、`2303-2026C1101-B024`。
