# KDOS 业务表格删除标准（table-delete-standard）

## 0. 目标与边界

### 0.1 目标

凡属于 KDOS 的**业务可维护表格**，都应具备与业务规则相符的删除能力及可发现的“删除”操作入口：

- 对具有该表**有效删除权限**的用户显示“删除”按钮；对没有该表有效删除权限的用户，**不渲染**删除按钮（不采用仅置灰作为权限控制）。
- 用户能够通过按钮实际提交删除；后端必须独立验证该表删除权限、租户、数据范围和业务状态，未授权返回 `403`。
- 删除操作有明确确认、结果反馈、审计追踪及关联数据处理规则。
- 优先复用现有 KDOS 共享表格、权限注册表和 Application Service，不为每个业务模块造重复框架。

这里“每个表”指每一个在适用范围内的**业务资源表格**，而不是任意 SQL 表、页面中所有统计子表或每个物理数据库表。规范定义的是功能与权限要求，**不会自动授予用户删除权限**。

### 0.2 适用

适用于用户有权新增、维护或纠错的业务记录，例如业务台账、分配记录、人工维护映射表、可维护计划明细、设备填报记录、物流业务记录、任务/项目中的可删除业务实体等。实际能否删除单条记录还取决于该记录的状态、关联、归属、数据范围及既有业务约束。

默认不适用：

1. E10/T+ 等 ERP **源系统只读表**、ERP 抽取原始表与只读投影；不能用 KDOS 删除功能删除 ERP 源数据。
2. 审计日志、操作日志、安全事件日志、不可变历史及法定留存记录。
3. 系统内部技术表（队列、outbox、幂等/游标、迁移、缓存、RLS/权限存储等）。
4. 纯统计 Dashboard、报表汇总表、查询结果表、只读视图，不代表可维护业务实体。

特别注意：即便资源已登记在 `tableResourceRegistry`，也**不**意味着它应该提供删除接口。对流程审批、已发布/锁定计划、入出库/报工等有业务影响的记录，必须遵循已有状态机和业务撤销/冲销规则；“撤销”“作废”“冲销”与“删除”不互相冒充。存在无法安全删除的情况时，在资源清单注明 `NOT_APPLICABLE` 或 `BUSINESS_RESTRICTED` 及原因，**不得通过绕过业务校验强行删除**。对例外资源的重新归类须有业务依据。

### 0.3 本项目触发与执行范围

- 新增或修改业务可维护表格时，读取本 Skill 核对删除能力是否适用；用户也可手工指定 `$table-delete-standard`。
- 加载本 Skill 不代表授权全项目改造、真实删除或授予权限。仅调整表头、布局等显示内容时，按本次影响核对已有约定，不主动增加删除接口、权限、数据库操作或回归范围。
- 本项目标准业务表遵循 `kdos-form-platform` 的工具栏删除约定，验收遵循 `kdos-form-validation` 的 L1/L2/L3 分级；已有特殊业务规则、归档/留存政策与用户当前授权保持优先。

## 2. 资源与删除权限判定

### 2.1 一表一权限

- 删除是独立的表动作 `delete`，不可借用 `read`、`create`、`update`、`import`、`batch_update` 或页面可见性代替。
- 当前 KDOS 使用形如 `${resource}:*:${action}` 的表动作权限；例如 `logistics-ledger:*:delete`、`equipment-status-report:*:delete`。资源名应从 `tableResourceRegistry` 等已登记资源中取值，禁止用中文显示名拼接权限。
- 保持现有权限来源：普通用户权限、权限组预设及数据范围、系统管理员、所属模块管理员。**有效权限**由既有统一授权机制判断；不要自行新增第二套 `isAdmin` 白名单、绕过管理员模型或只检查前端 `localStorage`。
- 没有生效删除权限，或权限请求尚未完成而无法确认为 `true` 时，删除按钮不可见。有效权限被撤销后，刷新页面及后续服务端请求均应反映撤销；服务端才是最终权威。
- 不自动修改 `presetTablePermissionMatrix` 或其他预设权限组，以免扩大现有用户权限。当前 `ADD_MANAGE_OWN` / `MANAGE_ALL` 具有删除动作仍须配合数据范围；并非所有组具有删除权限。

### 2.2 能力与权限双门槛

显示删除入口必须同时满足：

```
表格被认定为可维护业务资源
AND 该资源后端支持符合业务规则的删除命令
AND 当前用户具有该资源有效 delete 权限
AND 页面不处于禁止删除的特殊模式
```

单行是否能删除还要检查数据归属、表记录状态、关联记录及业务规则。按钮可显示，但选中的记录受限制时可以禁用并解释原因；这与**因无权限而隐藏按钮**是两个不同概念。

对于已有服务端资源元数据，优先复用 `actions.delete`（能力 × 有效权限），避免客户端自己推算后端是否存在删除能力。对没有元数据的业务模块，使用已有统一权限机制与正式后端能力约定，不得用路由存在与否作为“已授权”证据。

## 3. 前端 UI 标准

### 3.1 默认入口

- 使用 `KdosDataTable` 的业务表，优先使用 `deleteAction`，**默认采用勾选行 + 表格工具栏“删除”**；支持多选，表头操作和表格宽度保持 KDOS 现有布局。
- KDOS 标准业务表统一使用顶部工具栏删除，不在表内新增或保留 `⋯ → 删除`、独立行内删除按钮，遵守 `kdos-form-platform` 的既有规则。独立详情页等非标准列表的已有业务删除入口按该模块确认的规则维护，同一业务对象避免重复入口。
- 非 `KdosDataTable` 的自定义表格必须达到相同的权限、确认、反馈与审计效果；优先接入共享组件，避免复制删除逻辑。
- 没有 `delete` 权限：不渲染按钮及其菜单项，不使用 disabled/Tooltip 代替隐藏，不泄露仅管理员可执行的操作入口。
- 有权限但没有选择记录：允许显示处于禁用状态的“删除”按钮，提示“请先勾选要删除的记录”；选中不可删除记录，提示具体约束。
- 列表筛选、翻页后，确保选择的行 ID 可重新核实；对过期行不能悄然删除。

### 3.2 确认与反馈

- 提交前弹出二次确认，显示至少**选中条数**；单条优先显示业务可识别编号/名称；明确影响范围。针对业务有可恢复机制的记录，准确描述软删除/可恢复政策；否则提示后果，不一律写“不可恢复”。
- 点击确认后防止重复提交；取消不发出写请求。
- 成功时刷新当前表格/相关统计和缓存，清除已成功删除行的勾选状态；失败时解释原因。
- 对多条逐行删除，汇总成功数、失败数和失败原因；**不得将部分成功显示成全部成功**。
- 有关联任务、库存、报工、对账或衍生报表时，按模块既有机制触发必要的失效/对账刷新，不能只刷新浏览器列表就声称业务已完成。

### 3.3 已有组件示意（适配当前项目后使用）

```tsx
<KdosDataTable
  resource={resource}
  rowKey="id"
  // 其他已有表格属性保持不变
  deleteAction={metadata?.actions?.delete ? {
    permitted: true,
    canDelete: (row) => row.canDelete !== false,
    onDelete: async (rows) => {
      const result = await deleteTableRowsSequentially(
        rows,
        (row) => row.id,
        async (row) => {
      await api(`/business-module/resources/${resource}/${row.id}?expectedVersion=${row.version}`, { method: "DELETE" });
    }
      );
      await refreshTableAndDependencies();
      return result;
    }
  } : undefined}
/>
```

> 上述 `/business-module/...`、`refreshTableAndDependencies()` 是**占位示例**，不是仓库中现成路由/函数。必须换成该模块真实 API、版本参数和刷新机制，不能直接复制作为可运行代码。单条删除没有 `version` 时遵循该模块已有并发控制，不臆造字段。

## 4. 后端与业务正确性

### 4.1 强制服务端校验

所有删除必须走正式 Controller → Application/Command Service → Repository/受控事务路径。Controller 不直接操作数据库，Web 不直接操作数据库。至少校验：

1. 身份和有效表动作 `delete`，包括当前租户中管理员授权的有效性；没有权限 `403`。
2. 资源在服务端白名单内且支持删除；未开放删除不因客户端伪造而绕过。无能力可统一按现有 API 规范拒绝。
3. 租户边界（`tenant_id`、RLS/事务上下文）和行级/部门/个人数据范围；跨租户与越权不可删除。
4. 记录存在性、状态机及业务限制（发布、锁定、审批、已对账、报工、库存、关联子单等）；不可删除时解释规则并保持原数据。
5. 乐观并发版本/条件更新，存在冲突返回 `409`；使用已有记录版本机制，未支持时明确设计并发防护。
6. 对关联关系给出明确处置；默认不引入隐式级联删除，不通过关闭外键规避约束。

未登录按现有机制 `401`；无权限 `403`；不存在 `404`（须避免跨租户信息泄漏）；并发冲突 `409`；业务冲突沿用该模块已定义的 `409`/`422` 等语义。错误文案不应暴露其他租户的数据。

### 4.2 删除语义与审计

- **不统一强制软删或硬删**：复用原模块已确认的业务删除语义（如设备状态填报软删；部分主计划资源物理删除）。新建模块应先根据审计追溯、引用关系、ERP 同步与恢复需求选择策略并说明理由。
- 软删除需统一影响查询过滤、唯一约束/重建规则、导入与同步、恢复入口（若有）、报表统计；禁止删除后被定时同步无意恢复而不说明。
- 物理删除需确保数据保留政策允许、外键与关联无风险、审计保留最小必要的删除前信息。
- 关键删除操作写入现有审计体系，记录租户、操作人、资源、记录 ID、动作、时间、requestId/来源，按安全策略记录必要 before/after；敏感内容与凭据不得写入审计或日志。
- 业务数据删除与必须一致的审计记录在同一事务；外部派生更新通过已有 outbox/对账机制，支持失败重试或明确告警。
- 真实删除的数据授权和生效范围以**删除请求当时服务端重新解析**为准，不能信任页面加载时缓存的许可。

## 5. 接入和改造流程

1. **列清单**：仅在本次用户授权范围内枚举涉及的业务表格（明确要求全项目改造时再覆盖全项目），关联 `tableResourceRegistry` 资源码，归类为 `APPLICABLE`、`NOT_APPLICABLE`（ERP 只读/审计/技术/纯统计）或 `BUSINESS_RESTRICTED`（业务状态受限），记录现有删除入口、API、权限、数据范围和审计能力。
2. **先复用**：检查本表是否已有完整删除能力；已有且符合规范则不重复加按钮、不重建路由、不改变原有权限或删除语义。
3. **补齐能力**：适用但缺少入口/API 的资源，沿既有结构补充服务端删除命令、资源级 `delete` 权限、数据范围、业务约束、审计及前端 `deleteAction`。
4. **按影响验收**：遵循 `kdos-form-validation` 分级及用户测试授权，优先复用相关用例。涉及删除行为时覆盖权限、租户/数据范围、版本、关联和结果反馈；仅安装本 Skill 时只校验文档、适用范围与发现配置，不执行业务测试或真实删除。
5. **出变更报告**：列出已完成、可复用、需业务决策、排除的资源和对应原因。不得把“已登记权限”“只有按钮”“已有接口”“单测通过”单独当成完整交付。

如果本次任务仅要求建立 Skill，**只新增 Skill 和必要的 AGENTS 引用，不批量改造现有表格，不执行实际删除**。后续逐模块改造才执行相关应用测试与部署核验。现有正在运行系统、历史资料及数据保留边界不因 Skill 文档创建而变化。

## 6. 验收用例与通过标准

| 场景 | 预期 |
| --- | --- |
| 用户无本表有效 `delete` 权限 | 删除入口完全不可见；直接调用 API 返回 `403` |
| 用户只有 `read` / `update`，无 `delete` | 可正常使用已有授权能力；删除入口不可见 |
| 用户通过权限组取得删除权限 | 在可维护表内显示删除入口；仍受 OWN/部门/ALL 数据范围约束 |
| 系统/模块管理员按现有权限模型取得有效删除权限 | 对其授权模块显示删除入口；不因 UI 检查遗漏合法管理员 |
| 用户已被撤销删除授权，未刷新页面却提交请求 | 后端按当前授权拒绝；不发生删除 |
| 已授权但未选择行 | 显示删除按钮但禁用，提示先选择 |
| 已授权但行被锁定、发布或关联禁止删除 | 不实际删除；明确原因，不破坏业务状态 |
| 跨租户/超出行级数据范围 | 后端拒绝，不泄漏其他租户数据 |
| 版本冲突或行已被删除 | 不覆盖他人修改；反馈冲突/不存在 |
| 单条正常删除 | 数据按业务语义处理、审计完整、列表/派生数据刷新 |
| 批量删除部分成功 | 成功、失败数量和原因准确，成功行取消选择 |
| ERP 只读表、审计日志、系统技术表、纯统计报表 | 不因本 Skill 自动增加删除入口或写接口 |

后续业务实现按实际修改范围及用户测试授权，从现有权限单测、Application/API 集成检查、React 组件检查和真实浏览器中选择相关验证；不机械要求每次运行全部层级。只有涉及状态机、入库、报工、审批或 ERP 同步时，才增加对应验证。仅安装 Skill 不执行上述业务用例，不调用真实删除接口。

## 7. 完成报告格式

- 改动范围：模块、资源码、表格页面、Controller/Application、权限/数据范围、审计、测试文件。
- 资源分类：适用/排除/业务限制及依据；已有功能直接复用的比例。
- 删除实现：入口位置、权限读取来源、后端命令、软删/硬删/撤销语义、关联与对账影响。
- 权限核验：无权限隐藏 + 直调 403 + 有权限且数据范围内可用。
- 验证结果：单测、接口、E2E、lint/typecheck/build；指出未验证项。
- 交付状态：仅制定 Skill / 已实现未上线 / 已部署核验，三者不得混写。

## 8. 与其他项目规范的关系

本 Skill 补充 `AGENTS.md`、`SECURITY.md`、既有权限和业务状态机；出现冲突时不能降低权限隔离、审计、数据保护与业务约束。对于是否物理删除、是否允许批量删除、特殊资源是否属于可维护表的争议，先明确业务后再动手，不能凭“每个表”四个字扩大到源系统/内部库/不可变记录。
