# KDOS 表单与权限开发规范

把本文件视为凯南信息化平台中“表单设计—数据管理—权限管理”功能的强制产品与工程规范。实现、修改、审查或测试相关代码时，遵守下列规则。

## 1. 工作方式

1. 先检查当前仓库结构、现有实现、数据库迁移、接口、测试和未提交改动，再决定修改范围。
2. 优先复用现有技术栈、组件、字段定义和公共服务；不要为了套用本文而无理由重写正常模块。
3. 把本文中标为“固定”“必须”“不得”的内容视为验收条件，不得自行弱化。
4. 截图已确认的交互和权限状态优先于通用产品习惯；不要擅自增加截图中不存在的入口。
5. 遇到本文未定义且会显著改变业务结果的规则时，先列出缺口并询问；不要编造业务规则。
6. 前端只负责交互提示和视觉禁用，后端始终是权限、数据范围和字段安全的最终边界。
7. 修改后至少运行与改动相关的 lint、typecheck、单元测试和构建；无法运行时明确说明原因和未验证范围。
8. 输出结果时说明：修改了什么、关键规则如何落地、验证结果、仍存在的真实风险。

## 2. 核心范围与术语

- 租户：所有查询、写入、导出、广播、审计和缓存的第一层隔离边界。
- 表单：字段定义、布局、数据记录和权限组的归属单位。
- 权限组：对操作权限、字段权限、数据权限的组合定义。
- 授权对象：稳定 ID 标识的成员、部门或角色。
- 系统预置权限组：内部类型固定，只有显示名称可改。
- 自定义权限组：管理员可配置名称、说明、操作、字段和数据范围。
- 本人数据：`创建人 = 当前登录用户`，由后端根据认证身份动态解析。
- 全部数据：当前租户与当前表单内的全部数据，不得突破租户边界。

## 3. 数据表统一规则

### 3.0 模块导航层级

- 每个模块左侧的主标签，以及任意层级中包含子标签或文件的标签，都必须使用可收起/展开的树形菜单节点；不得用不可折叠的静态分组标题承载子项。没有子标签或文件的叶子标签直接导航，不显示伪展开按钮。新增模块、文件夹、业务表或报表时继续遵守同一规则。
- 同一层级的标签必须使用统一的字体族、字号、字重、行高和缩进；选中、悬停和展开状态只能改变颜色、背景或状态标识，不得改变字号、字重、字体族或文字基线。互为同级的标签必须统一图标策略：要么都有同尺寸图标，要么都不显示图标，不能因单个标签有无图标造成文字错位。

### 3.1 表格能力

- 所有独立业务表单和报表遵守统一的基础表格交互规范，但不得机械复制其他业务表的专属字段、按钮或行级操作。通用结构为：左侧放“进入/退出编辑模式”和经批准的业务操作，右侧放搜索、筛选、字段显示及该表已批准的操作；表格使用白色容器、固定表头、统一行高与悬停色，分页固定在表格右下角。权限管理页必须存在，但本条不强制其入口位置，也不得在业务表格中显示“权限入口位置”之类的说明文字。
- 所有独立业务表单和报表必须分页；默认每页 `50` 条，允许选择 `20 / 50 / 100 / 200` 条，显示总条数并支持翻页和快速跳页。切换每页条数、搜索或筛选后，当前页必须回到第一页，防止停留在不存在的页码。每页条数可以按“用户 + 表单资源”保存为个人偏好，但不得改变其他用户或权限范围。
- 主计划等必须保留 AG Grid Community 的宽表可以继续使用 AG Grid，但其分页能力、每页条数选项、总数提示和位置必须与上述统一表格一致，不得以虚拟滚动为理由取消分页。
- 所有表格的分页、页码、每页条数、总数、跳页、加载、空数据、列菜单、排序、筛选、固定字段、复制和导出等可见文案与辅助提示必须使用中文；不得出现 `Page Size`、`Page 1 of 88`、`Columns`、`Filters`、`Sort Ascending` 等英文，也不得依赖组件库的英文默认值。Ant Design 统一挂载中文语言包，AG Grid 必须显式传入完整中文 `localeText`。
- 每个可筛选字段的字段名旁必须提供统一的筛选按钮；按钮、悬浮提示、弹层标题、条件名称和操作按钮全部使用中文。字段筛选至少提供“包含”的即时文本查找、回车应用、“筛选”和“清除”，并与顶部标准筛选面板共享同一筛选状态，不得形成两套互相冲突的条件。
- 字典/选项类字段（数据库保存稳定 `value`，界面显示中文 `label`）的筛选必须在服务端先按字段自身的 `options` 定义把输入解析成真实 `value` 再查询：输入 `value` 或 `label` 都必须命中，模糊输入按 label/value 解析成全部匹配项后使用 `= ANY(...)`，匹配不到任何选项时返回 0 行；禁止直接把显示名称送给数据库 `value` 列做模糊匹配，也禁止在控制器、服务或前端另写第二份字典映射。列表、待办视图、全局搜索与导出必须共用同一解析逻辑，保证同一筛选条件得到同一数据集。
- 顶部快速搜索对应 Excel 的“查找”，字段名旁筛选对应 Excel 的“自动筛选”。筛选弹层应自动聚焦输入框、允许清空、支持回车应用、突出显示已生效条件，并在条件变化后返回第一页；日期、数字、字典、成员和部门字段应逐步使用匹配其类型的条件与候选值，不得长期把所有字段退化成不可解释的自由文本。
- 类型化高级筛选（KN-FILTER-001）：正式筛选协议是 `FilterGroup { logic: "AND" | "OR"; rules: FilterRule[] }`，`FilterRule` 只包含 `field` + `operator` + 操作数（`value`/`values`/`min`/`max`/`dynamic`）；客户端不得提交字段类型、列名、SQL、table、join、cast 或表达式，类型永远由服务端字段 metadata 决定（`@kdos/contracts` 的 `TablePermissionFieldType`：text/number/date/datetime/boolean/dictionary/member/department/reference/structured/attachment）。时间戳必须用 `datetime`（不得当 `date`），关联字段必须用 `reference` 并声明候选来源资源，数组/多值字段必须显式 `multiple: true`，数值必须声明 `format`（integer/decimal/percentage/durationMinutes/currency），JSON 字段必须显式声明 `filterable` 策略。
- 服务端筛选编译器（`master-plan.filter.ts` 的 `MasterPlanFilterCompiler`，后续模块复用同一实现与 `tableFilterOperatorsFor` 操作符 registry）必须做到：字段 allowlist（未知字段拒绝）、操作符必须属于该字段类型（不匹配拒绝）、操作数类型化校验（数字/日期/关键字）、全部值参数化（禁止拼接用户输入）、字段读权限校验（无 read 权限的字段不得筛选，防止隐藏字段侧信道推断）、`tenant_id` 与数据范围在筛选之前生效、动态日期（today/yesterday/this_week/last_week/this_month/last_month/last_7_days/last_30_days/this_year）由服务端按 Asia/Shanghai 计算。类型化筛选与既有自由文本筛选必须共用同一条件入口，列表、总数、分页、导出与 PENDING 视图必须使用同一个编译器，保证页面筛选与导出结果一致。

#### 3.1.0.1 平台筛选能力登记与接入（KN-FILTER-001 第四轮，强制）

- **唯一编译器**：平台实现只有 `apps/api/src/common/filtering/sql-filter.compiler.ts`（`SqlFilterCompiler`）与 `filter.contract.ts`；任何模块不得再写第二套筛选/字典/日期逻辑。TypeORM 模块通过 `applyTypedFilterToQueryBuilder()` 复用同一编译器（`:filter_n` 命名参数），原生 SQL 模块直接用 `$n` 占位符。
- **能力登记唯一来源**：`@kdos/contracts` 的 `tableFilterResourceCapabilities` 必须覆盖全部正式 resource，状态只能是 `REGISTERED_AND_FILTERABLE` / `REGISTERED_NOT_FILTERABLE` / `NOT_APPLICABLE` / `BLOCKED`，禁止 UNKNOWN 或“暂未处理”；`NOT_APPLICABLE` 与 `BLOCKED` 必须写明原因。`TableFilterBootstrapCheck` 在启动时断言声明集合与运行时 `TableFilterRegistry` **完全一致**，少注册或多注册都让应用启动失败。
- **新增 resource 必须注册筛选能力**：新表上线时同时完成（1）契约字段 metadata，（2）`TableFilterRegistry` 注册（表、列绑定、`tenantColumn`、数据范围构造），（3）服务端 list 真正接收并应用 `filterGroup`。未完成前 `KdosDataTable` 只能显示禁用按钮“高级筛选（暂不支持）”，不得出现“可填写但服务端忽略”的假筛选。
- **不许伪造租户条件**：`tenantColumn` 默认 `tenant_id`；ERP 镜像表与审计日志等确实没有租户列的资源必须显式声明 `tenantColumn: null`，隔离由资源权限与数据范围承担。
- **data scope 不得全局假定 `created_by`**：`OWN` 的含义必须服从该资源既有正式语义（示例：设备按事业部/本人，供应商按范围规则，主计划按事业部）。平台 `buildScope` 必须与该模块列表未筛选时的权限完全一致，candidate 与 list 必须共用同一构造。
- **reference 禁止猜 label**：关联候选标签只能来自字段 `filterBinding.labelField` 或 `tableReferenceLabelFields` 的显式声明；缺失即 metadata 审计失败并在 candidate 接口返回 400，禁止“回退目标资源前两个文本字段”。
- **正式 UI 操作符白名单**：界面只暴露 `tableFilterUiOperatorsFor()` 的结果——文本/字典/成员/部门/关联/多值各有固定集合；`starts_with`、`count_eq/count_gte/count_lte`、数值 `in/not_in` 等内部能力不得出现在正式界面。文本字段默认条件为“包含”，与列头筛选一致。
- **Header 与 Advanced 是同一个 FilterGroup**：两者必须读写同一 `filterGroup`，草稿与应用态分离，只有点击“筛选/清空”才写 applied 并请求；条件变化回到 `page=1`。
- **时长与百分比必须类型化输入**：`durationMinutes` 让用户填“小时 + 分钟”（10 小时 30 分钟 = 630，BETWEEN 480~630），`percentage` 界面为 0..100、提交前换算（80% → 0.8），数据库仍比较整数分钟/小数，不得让用户直接输入分钟或 0.8。
- **字典解析不得引用不存在的列**：`dictionary_values` 只有 `value`（无独立 label 列）时按 value 精确命中；动态字典应优先提升为平台共享解析服务。
- **审计字段按真实 schema 登记**：`updated_by` 多数表是 varchar（可存 system/迁移标识）→ `text`；`created_by` 通常是 member；`created_at/updated_at` 是 `datetime`。允许 resource 级 override，禁止只按字段名统一语义。

#### 3.1.0 行选择与行级操作（强制）

- 所有标准业务记录表默认支持记录选择。记录选择与“进入编辑模式”必须彻底分离：表格处于只读浏览模式时也允许用户选择其有权查看的记录；选择记录本身不代表拥有编辑、删除、批量修改、导出或其他写入权限。任何后续操作仍须根据操作权限、字段权限、数据范围和业务状态重新校验。
- 表格最左侧固定提供 checkbox 选择列；该列属于前端 UI 状态，不是业务字段，不得进入数据库、ORM 实体、API DTO、字段注册表、字段权限、导入模板或导出字段。宽表横向滚动时，选择列应保持固定可见。
- 表头提供当前页全选 checkbox。默认“全选”只选择当前页，不得把当前页全选解释为当前筛选范围或数据库全量选择。支持单选、多选、取消单条、取消当前页全选和清空全部选择。
- 选择状态必须使用稳定记录 ID 保存，不得使用数组下标、当前页序号、显示文本或 DOM 位置作为记录身份。允许跨页保留用户已经明确选择的记录；分页、排序后不得发生选择串行。搜索、筛选或切换页面不得静默扩大已选范围。
- 选中记录后，表格顶部显示选择状态栏，至少提供“已选 N/M”和“清空选择”。`N` 为当前实际选中记录数；`M` 为当前权限和筛选范围内可选择的总数，不得用当前页行数冒充总数。
- 所有独立业务表格默认不得创建固定名称为“操作”的宽列。“操作”不是业务字段，不得进入数据库、API、字段权限、导入模板、导出字段或表单字段注册表。
- 需要行级查看、编辑、删除、停用等操作时，网页版统一优先使用紧凑的 `⋯` 更多菜单承载低频行级操作；不得默认使用右键菜单作为唯一入口，也不得机械给所有表格添加同样的行级动作。是否显示每个菜单项必须同时受当前产品能力、操作权限、数据范围和业务状态控制。
- 双击编辑、单元格编辑等现有交互可以继续使用；`⋯` 更多菜单主要用于查看、删除、停用等不适合直接暴露为常驻列按钮的操作。删除、停用等高风险操作仍须二次确认并由后端重新校验。

#### 3.1.1 表格读取、缓存与服务端分页（强制）

- 所有业务记录表必须由后端完成权限裁剪、搜索、字段筛选、排序和分页后再返回当前页；不得先向浏览器返回整表再做客户端分页或筛选。统一页大小默认为 `50`，只接受 `20 / 50 / 100 / 200`，后端硬上限为 `200`。响应至少包含 `rows`、当前权限和筛选范围内的 `total`、`page`、`pageSize`。确实不会增长且数量很小的字典、下拉选项和聚合结果可以整表返回，但不得把持续增长的业务记录表归为该例外。
- 查询参数必须使用服务端允许名单中的稳定 `field_key` 和排序键，值使用类型化、参数化查询；不得接受客户端 SQL、任意数据库列名或可执行表达式。总数、分页记录、导出和汇总必须应用相同的租户、表单、数据范围和字段权限边界。
- 前端表格查询必须缓存。缓存键至少包含租户、登录用户或权限上下文版本、表单资源、页码、每页条数、排序、标准化搜索与筛选条件；不得跨租户、跨用户或跨权限范围复用业务数据。退出登录、切换账号/租户、权限组或数据范围变化时，立即清除或精确失效相关缓存。
- 在缓存保鲜期内重新进入页面或切回已访问分页时直接显示缓存，不得因组件重新挂载自动重复读取。翻页、搜索或筛选时保留上一页内容直到新页返回，避免整表闪空。元数据和小型静态选项默认缓存 `5` 分钟，业务表页默认缓存至少 `60` 秒；实时协同表可以设置更长保鲜期，但必须由可靠的失效事件保证新鲜度。
- 数据写入成功、导入确认、同步完成、删除、权限变化及相关实时事件必须精确失效受影响的表格页、总数和聚合查询。WebSocket 只发送租户、资源、记录/版本及变化类型等失效元数据，客户端收到后重新读取授权数据；不得在事件中传完整敏感记录。提供手工刷新入口的表格，刷新只重新读取当前查询，不得触发外部导入或同步。
- HTTP `304`、浏览器 ETag 或网络缓存不能替代应用查询缓存和服务端分页，因为控制器和数据库查询可能已经执行。首次打开、强制刷新、缓存过期或失效事件后的重新读取属于正常刷新；普通页面往返不得反复加载整表。
- AG Grid 使用服务端/无限行模型或等价受控分页时，序号按全局偏移计算，排序和筛选作用于完整权限范围，勾选使用稳定记录 ID，并按产品规则保留跨页选择；不得把当前页排序、筛选或当前页行数冒充全量结果。
- 至少测试：保鲜期内重新进入不发起重复列表请求；翻页、页大小、搜索、字段筛选和排序返回正确记录与总数；写入和实时事件会失效缓存；退出或权限变化后旧数据不可见；伪造字段、排序键、页大小或身份不能突破租户和数据权限。

#### 3.1.2 企业微信推送项目目录（强制）

- 计划中心所有新增企业微信推送任务必须放在 `automation/wechat_push_projects/`，每个任务使用独立子文件夹；配置、业务状态文本、图片模板、测试、运行说明和服务模板不得散落到其他业务模块。
- 企业微信和通讯录统一调用 `/data/automation/code/work/basci/basic_code` 的 `WeChatPusher`，密钥只留在该工具包自己的 `.env`，不得复制到仓库、配置 JSON、日志、测试数据或图片中。
- 推送任务默认只能预览或生成内容；测试接收人与正式接收人分开配置，首次上线先单人实发。正式群发必须使用与测试参数不同的显式确认开关，未明确发送时间时不得擅自启用周期定时器。
- 所有数据表格首次打开、刷新、重新进入页面或切换表格时，必须处于纯文本只读浏览模式；无论当前用户是否拥有编辑权限，都不得自动进入编辑状态，也不得直接向用户展示输入框、日期选择器、人员选择器等编辑控件。
- 编辑权限只决定用户是否有资格看到并使用“进入编辑模式”入口，不能作为自动进入编辑模式的条件。没有编辑权限时不得显示该入口；拥有编辑权限时也必须由用户主动点击后才进入编辑模式。
- 进入编辑模式后，只允许对字段权限为可编辑、且数据范围允许修改的记录展示编辑器；系统字段、只读字段和范围外数据仍保持只读。后端仍须对每次写入重新校验操作权限、字段权限和数据权限。
- 编辑模式必须有明显状态提示，并提供明确的退出方式。退出、刷新、重新进入页面或切换表格后必须恢复只读浏览模式；不得把编辑模式持久化为用户默认状态。
- 删除、停用等高风险操作不得因进入编辑模式而自动执行，仍须通过独立、明确的操作入口和后端权限校验。
- 支持双层分组表头、横向虚拟滚动和大数据量虚拟渲染。
- 对主计划类宽表固定关键列；至少保证序号、订单号、品号、品名在横向滚动时可定位。
- 支持筛选、排序、搜索、列显示/隐藏、列宽调整和个人视图保存。
- 支持方向键、Tab、Enter、双击编辑、复制粘贴、TSV 多单元格粘贴、撤销/重做和查找。
- 支持单元格编辑、字典下拉、日期选择、数字校验、批量粘贴和批量保存。
- 图片字段显示缩略图并支持预览；上传、替换和删除必须受字段权限与附件权限控制。
- 保存失败必须定位到具体记录和字段并显示原因，不得只提示“保存失败”，也不得整页静默失败。

#### 3.1.3 批量修改界面与行为

批量修改必须参照 `docs/images/批量修改界面.jpg`，并遵守本节固定规则。该截图只用于确定“批量修改”的选择状态、弹窗结构和操作流程；截图中出现的批量打印等其他入口不属于本节授权范围，仍须遵守本文“不得显示批量打印入口”的规定。

**入口与选择状态**

- 记录选择能力始终存在，并且与编辑模式独立。表格默认以只读浏览模式打开时仍允许选择记录，但选择本身不得触发任何写入操作。
- 只有用户主动进入编辑模式、拥有当前表单的 `batch_update` 权限，并且当前选择中至少包含一条用户有权管理的记录时，才显示和启用“批量修改”。
- 未进入编辑模式时，即使已经选择记录，也不得出现可执行的批量修改、批量删除或其他未经授权的写操作。
- 选中记录后，表格顶部显示选择状态栏：提供关闭/清空选择入口，并明确显示“已选 N/M”；`N` 是实际选中记录数，`M` 是当前权限和筛选范围内可选择的总数，不得用当前页行数冒充总数。
- 允许跨页保留选择，但客户端必须保存稳定记录 ID 和选择快照，不得把“当前筛选全部”解释为不受边界限制的全库更新。搜索、筛选或切换页面不得静默扩大已选范围。
- “批量修改”必须是选择状态栏中的独立按钮，不得让用户通过直接框选后立即写入，也不得因拥有权限而自动打开弹窗。

**弹窗固定结构**

- 弹窗标题固定为“批量修改”，标题旁显示“本次操作将修改 N 条数据”，且数量必须与提交的选择快照一致。
- 标题下方显示规则提示：单次最多修改 `50000` 条数据；超过上限时不得打开可提交状态，也不得由前端拆成多个请求绕过限制。
- 明确提示以下字段类型不支持批量修改：图片、附件、定位、手写签名、选择数据、查询、分割线、文字识别、按钮。
- 第一项固定为“请选择需要修改的字段”的单选下拉框；一次批量操作只能修改一个字段。
- 第二项固定为“修改为”。未选择字段时该区域禁用；选择字段后，根据字段类型显示文本、数字、日期、字典、成员、部门等对应的类型化编辑器，不得统一退化为文本输入。
- 切换目标字段时必须清空前一字段的草稿值，避免把旧值按错误类型提交。必填、长度、精度、日期、字典有效值等校验与单行编辑保持一致。
- 弹窗左下角固定提供“查看修改记录”，进入当前租户、当前表单的批量修改历史；右下角固定为“取消”和“确定”。未选择字段或新值未通过校验时，“确定”不可提交。
- “取消”、关闭弹窗或按 Esc 均不得写入数据，并保留原表格的勾选状态；成功完成后刷新服务端数据并清空本次选择。
- 保存期间“确定”进入加载状态并禁止重复提交。界面不得额外增加截图中没有的自动执行、自动分批、默认值覆盖或跳过确认流程。

**可修改字段范围**

- 字段下拉框只显示当前用户对全部已选记录都具备编辑权限、且表单定义允许批量修改的业务字段；不得先展示无权字段再等提交时报错。
- 创建人、创建时间、更新人、更新时间以及任何系统字段、自动编号、计算字段、表单只读字段，永远不得出现在候选项中。
- 数据范围不同导致某条记录不可管理时，该记录不得混入可提交选择；前端提示具体数量，后端仍须逐条重新校验，不能信任前端筛选结果。
- 普通日期字段使用真实日期值和日期编辑器；界面可以按产品规则显示为“X月X日”，但不得把显示文本写入日期字段。

**提交、并发与审计**

- 提交命令至少包含租户上下文、表单资源、稳定记录 ID/受控选择快照、目标 `field_key`、类型化新值、各记录期望版本和幂等键；禁止接受客户端 SQL、显示名称字段或不受控筛选表达式。
- 后端对每条记录重新执行：身份与租户校验、`batch_update` 操作权限、数据范围、字段可编辑权限、字段类型与业务规则、乐观锁版本校验。任何失败都必须返回记录和字段级原因，不得静默跳过。
- 接口返回成功数、失败数和逐项结果。界面必须明确展示失败记录及原因，并允许用户按失败项重新选择；不得用“操作成功”掩盖部分失败。
- 每条成功记录都必须更新“更新人、更新时间”，不得改动“创建人、创建时间”。首次创建规则不因批量修改而改变。
- 批量修改写入独立操作审计，至少记录 `batch_id`、操作人、租户、表单、请求 ID、目标字段、提交数量、成功/失败数量和幂等键；每条成功记录保留变更前后值，每条失败记录保留受控错误原因。审计展示仍受字段可见权限和脱敏规则约束。
- “查看修改记录”读取服务端审计结果，不得读取仅存在浏览器内的临时日志；无审计查看权限时后端拒绝访问，不能只隐藏链接。

### 3.2 字段与数据类型

- 每个字段使用不可变的 `field_key`；显示名称修改不得改变字段身份。
- 未注册的 `field_key` 不得写入数据库。
- 订单号、品号、关联信息、供应商名称等标识值按字符串保存，保留前导零。
- 关联信息可由订单号与品号生成，但数据库仍须建立独立的业务唯一约束。
- 日期使用 ISO `YYYY-MM-DD`，数据库使用 `date`；不要把纯日期误存为带时区时间。
- 数量根据业务使用整数或 decimal；所需天数必须允许 `0.5` 等小数。
- 金额使用 PostgreSQL `numeric` 或等价精确十进制类型，禁止用浮点数处理金额。
- 明确区分空字符串、`null` 和数值 `0`。
- 图片与附件在数据库中只保存元数据、相对路径或受控 URL，不保存前端临时地址。
- 部门、责任组织等明确的组织归属字段必须使用统一的“部门”字段类型，持久化稳定部门 ID；名称和完整路径只能作为展示或历史快照，禁止用名称、末级名称或拼接路径承担关联、唯一性、权限或同步键。
- 营销业务表中的“课室”是普通文本字段，不是组织节点；不得使用部门选择器、稳定部门 ID、部门负责人权限或组织子树解析。只有用户明确要求将某个课室建模为企业微信组织节点时，才允许变更这一规则。
- 部门字段编辑器必须展示完整组织路径，并允许同一棵树中不同层级、不同分支出现同名部门。旧数据或 Excel 只提供名称时，服务端必须结合父子拓扑解析；唯一性无法确认时拒绝写入并返回候选完整路径，不得猜测或扩大匹配范围。
- 组织架构的权威来源为企业微信。同步必须保留外部部门 ID、父部门、层级、排序、启用状态和每个部门的负责人集合；`is_leader_in_dept` 按成员—部门关系解析，支持一个部门多负责人和一名成员负责多个部门。

### 3.3 强制系统字段

每张业务数据表必须包含且只包含以下四个系统审计字段，顺序固定：

- 创建人
- 创建时间
- 更新人
- 更新时间

这四个字段由系统维护，必须满足：

- 在查看权限允许时可见，但永远不可编辑。
- 不得通过新增表单、数据表格、批量修改、导入、API、WebSocket 或任何权限配置修改。
- 后端必须忽略或拒绝客户端对这些字段的赋值和篡改。
- 创建人和更新人在数据库中保存稳定用户 ID；表格、详情、导出等用户界面必须通过通讯录显示姓名，不得显示 ID 编号，也不能把姓名作为身份依据。
- 用户离职、停用或改名后，历史数据仍应正确关联原用户记录。
- 首次创建记录时，创建人必须等于更新人，创建时间必须等于更新时间；后续修改只更新更新人和更新时间。
- 不得设置 `审计时间`、`auditedAt` 或 `audited_at` 业务表字段。操作审计仍写入独立审计日志，并与关键业务写入处于同一事务。

### 3.4 保存与并发

- 在后端事务中完成权限校验、字段校验、数据写入、必要的派生计算和审计记录。
- 使用版本号或等价机制实现乐观锁；冲突返回明确的 409 响应和当前服务端版本。
- 保存成功后以服务端返回值覆盖客户端预览值。
- 实时广播前再次按接收者的租户、数据范围和字段权限裁剪数据。

## 4. 权限管理页

### 4.0 权限主界面（替代旧入口和全局矩阵规则）

本节以 `docs/images/权限主界面说明.md`、`权限主界面.png`、`新增了权限后的权限主界面.png` 及同目录“权限组”系列截图为唯一界面依据；旧的全局角色矩阵、“为表单添加权限组”表单和固定入口说明不再使用。

- `tableResourceRegistry` 中每个独立表单或报表都必须有自己的权限管理页；登记资源但没有可访问权限页，或显示表格却没有登记资源，均为验收失败。
- 页面必须明确显示“对成员发布”和当前表单名称，并提供“返回原表”；禁止用没有资源上下文的全局矩阵代替单表权限页。
- 页面没有权限组时，主区域只显示“添加成员”主按钮和必要导航，保持截图中的空白主视图，不得自动创建默认组或堆放说明卡片。
- 页面已有权限组时，左上继续显示“添加成员”，右侧显示“停用全部”，中间按权限组卡片展示。
- 页面访问、读取和写入接口均由后端验证权限；是否显示入口不是授权边界。入口位置服从当前产品导航，不在表格页面额外显示“权限入口位置”“前端按钮不是授权边界”等说明文案。

### 4.1 权限组卡片

每个权限组以独立卡片显示，包含：

- 权限组显示名称。
- 虚线区域中的已授权成员、部门和角色标签；标签必须能区分对象类型。
- 卡片右侧依次提供编辑、复制、其他设置、删除和启停开关；不增加截图中没有的“配置权限”入口。

规则：

- 卡片排序只影响展示顺序，不影响权限优先级。
- 系统预置权限组不得因改名而改变能力。
- 自定义权限组可以完整编辑；系统预置权限组只有显示名称可编辑。
- 权限组停用后，只移除该组贡献的权限，不影响用户从其他组获得的权限。
- “停用全部”只影响当前表单中的权限组，并须二次确认；不得影响其他表单、普通角色或系统管理员能力。
- 删除、停用和批量变更必须经过后端校验并写入审计。

### 4.2 授权对象与权限叠加

同一用户可以同时通过以下来源获得权限：

- 直接选择为成员。
- 所属部门。
- 所属角色。
- 其他已启用权限组。

有效授权按来源并集计算：

```text
用户有效权限 =
直接成员权限
∪ 部门权限
∪ 角色权限
∪ 其他已启用权限组权限
```

补充规则：

- 部门和角色授权是动态关系；成员加入或离开后，有效权限随组织关系变化。
- 在角色成员界面以部门为单位选择时，必须保存“角色—部门稳定 ID”关系，不得把当时的成员快照展开成静态“角色—用户”关系。成员当前属于该部门或其子树时动态获得角色；调离该部门、离职、停用或移出租户后立即失去该来源的角色；新入职或调入该部门后自动获得角色，无需管理员重新保存。
- 同一角色允许同时存在部门授权和直接成员授权，两种来源按并集计算并在界面区分。移除部门授权不得删除直接成员关系；部门授权中的单个人员不能通过取消人员勾选形成隐式例外，需要例外规则时必须另行设计显式模型。
- 部门身份只能由租户内稳定部门 ID（以及同步源的稳定外部 ID）确定；部门名称和名称路径只用于展示，允许不同层级或不同分支出现同名部门，任何筛选、勾选、授权、缓存和审计都不得把名称当作唯一键。
- 对仍只提供名称路径的旧通讯录数据，必须在组织适配层结合完整拓扑解析到最具体的稳定部门 ID。连续同名层级被同步源省略时，解析到同一路径中最深的唯一节点；若同一深度仍有多个候选则拒绝自动归属并暴露数据质量问题，不得扩大到同名父部门、兄弟部门或其他分支。
- 部门授权固定覆盖该部门的完整组织子树：包含该部门本身、所有层级的子部门，以及直接或间接归属这些部门的全部成员。直接挂在上级部门、没有归属到任何子部门的成员也必须包含在有效授权范围内。
- 界面可以把完整子树展开为勾选状态和人数统计，但持久化时优先保存用户实际选择的部门稳定 ID，由后端动态解析完整子树；不得为了表现级联选中而重复保存同一部门或成员授权关系。
- 如果部门和成员同时被选择，两条授权关系都要保留，移除部门授权不能连带删除个人授权。
- 离职、停用或被移出租户的用户立即失去有效权限；历史配置和审计记录保留。
- 部门负责人数据权限使用动态值“当前用户负责的部门及子部门”：每次受保护请求根据最新组织架构和负责人关系解析当前用户直接负责的部门，再展开完整子树。负责人变更、调岗、离职或停用后该来源权限立即失效；新负责人同步后自动生效。不得把配置当时的负责人或成员展开为静态用户名单。
- 部门负责人权限只能匹配部门字段中保存的稳定部门 ID，并由后端在查询、导出、详情、修改、删除和批量操作时强制执行；前端过滤、列隐藏或按钮隐藏不得作为授权边界。
- 不得因姓名相同把历史权限转移给新用户。
- 权限计算和缓存键必须包含租户、表单、用户与版本信息；变更后立即失效相关缓存。

## 5. 添加成员流程

添加成员必须是两步流程。

### 第一步：选择授权对象

- 弹窗标题为“部门成员列表”，顶部虚线区域显示当前已选对象并允许逐项移除。
- 搜索框位于虚线区域下方，支持按空格分隔多个关键词；搜索结果不得改变已经选择但暂时不在结果中的对象。
- 固定提供“组织架构、角色、成员”三个标签，支持选择整个部门、按角色选择、直接搜索或按组织筛选后选择成员。
- “组织架构”显示完整部门树并支持勾选整个部门。勾选任一上级部门时，必须默认同时勾选该部门本身、其所有层级的子部门，以及直接或间接归属这些部门的全部成员；直接归属该上级部门且未归属任何子部门的成员不得遗漏。树节点、成员列表和“已选 N/M”必须立即反映完整级联结果，不得要求用户逐层展开后再手工勾选。“角色”按角色组和角色的层级展示并可分别勾选；角色组本身只是选择其包含角色的快捷方式，不作为授权对象保存。
- 未选择任何对象时，“确定”按钮禁用。
- 选择结果保存稳定 ID，不得只保存名称。
- 成员标签使用左右两栏：左侧显示“全部成员”和组织架构树；点击部门筛选右侧成员。
- 右侧显示当前范围成员，顶部显示“已选 N/M”。
- 每名成员显示头像、姓名和复选框。
- 当前结果提供全选框，并正确显示全选、半选和未选状态。
- 弹窗左下保留“通讯录”入口，右下固定为“取消、确定”。点击“确定”后进入第二步，不立即写入正式授权关系。

### 第二步：选择成员权限

弹窗包含：

```text
对成员发布
[已选择的成员、部门或角色]

成员权限
[权限下拉框]
```

规则：

- 点击“对成员发布”虚线区域，返回第一步重新选择。
- 返回第一步时保留原选择；再次确认后回到第二步。
- 已填写的自定义权限内容不能因返回选择对象而丢失。
- 最终点击“确定”后，把授权对象和权限一次性保存。
- 点击“取消”、关闭弹窗或中途退出，整个流程不生效。
- 本步骤中的权限下拉框只能单选。
- 保存期间主按钮进入加载和禁用状态，防止重复提交。
- 保存失败时弹窗不得关闭，必须保留授权对象、自定义权限配置和当前标签，并在弹窗内显示具体原因。

### 权限下拉框

按以下结构显示：

```text
已有自定义权限组
  [已有自定义权限组名称]

系统预置权限
  仅添加数据
  添加并管理本人数据
  添加并查看全部数据
  管理全部数据
  查看全部数据

＋新建自定义权限
```

- 已有自定义权限组是可选择项，不是编辑按钮。
- 选择已有组后，把对象加入该组；已有卡片时追加成员，不重复建组。
- 同一对象不得在同一权限组中重复授权。
- 允许选择一个尚未授予任何能力的已有自定义组，但保存前提示加入后仍无法访问数据。
- “＋新建自定义权限”创建独立权限组；选中后权限下拉框显示“自定义”，并在其下方展开完整权限编辑界面。

## 6. 系统预置权限组

系统固定五种内部类型：

| 显示名称 | 内部类型 |
|---|---|
| 仅添加数据 | `ADD_ONLY` |
| 添加并管理本人数据 | `ADD_MANAGE_OWN` |
| 添加并查看全部数据 | `ADD_VIEW_ALL` |
| 管理全部数据 | `MANAGE_ALL` |
| 查看全部数据 | `VIEW_ALL` |

共同规则：

- 只允许修改 `display_name`。
- 禁止修改 `group_type`、固定说明、操作权限、字段权限和数据权限。
- 前端用灰色禁用控件展示只读权限；后端必须拒绝或忽略越权修改，不能只依赖前端禁用。
- 修改显示名称必须写审计日志，且不改变内部类型或实际能力。

### 6.1 固定操作权限矩阵

| 操作 | 仅添加 | 添加并管理本人 | 添加并查看全部 | 管理全部 | 查看全部 |
|---|:---:|:---:|:---:|:---:|:---:|
| 查看 | 否 | 是 | 是 | 是 | 是 |
| 添加 | 是 | 是 | 是 | 是 | 否 |
| 复制 | 否 | 是 | 否 | 是 | 否 |
| 编辑 | 否 | 是 | 否 | 是 | 否 |
| 删除 | 否 | 是 | 否 | 是 | 否 |
| 批量打印 | 否 | 是 | 是 | 是 | 是 |
| 批量修改 | 否 | 是 | 否 | 是 | 否 |
| 导入 | 否 | 否 | 否 | 否 | 否 |
| 导出 | 否 | 是 | 否 | 是 | 否 |

“全选”根据矩阵显示全选、半选或未选，但在预置组内不可点击。

### 6.2 仅添加数据 `ADD_ONLY`

- 固定说明：`在此分组内的成员只可以填报数据`。
- 编辑弹窗左侧只显示“名称信息”，不显示操作、字段和数据权限标签。
- 成员可以打开新增表单、填写并提交数据。
- 成员不能进入数据管理页查看记录，也不能查看、复制、编辑、删除、导入、导出或批量修改数据。
- 新增表单的可填写性遵守表单字段自身定义；系统字段仍不可编辑。

### 6.3 添加并管理本人数据 `ADD_MANAGE_OWN`

- 固定说明：`在此分组内的成员可以添加并管理本人提交的数据`。
- 数据范围固定为 `创建人 = 当前用户`。
- 查看、复制、编辑、删除、批量修改、导出、搜索、筛选和汇总都只能作用于本人提交的数据。
- 复制本人记录后，新记录的创建人和更新人必须是当前登录用户。
- 批量操作必须逐条在后端验证数据范围。
- 全部字段可见；普通可编辑字段可编辑；自动编号、计算、表单只读和系统字段不可编辑。

### 6.4 添加并查看全部数据 `ADD_VIEW_ALL`

- 可以添加数据、查看当前租户当前表单的全部数据和使用预留的批量打印权限。
- 不能复制、编辑、删除、批量修改、导入或导出已有数据。
- 查看已有数据时全部字段可见且只读。
- 新增数据时仍按表单字段定义填写允许输入的字段。

### 6.5 管理全部数据 `MANAGE_ALL`

- 固定说明：`在此分组内的成员可以管理全部数据、填报数据，但不可以导入数据`。
- 数据范围固定为当前租户当前表单的全部数据。
- 拥有查看、添加、复制、编辑、删除、批量打印、批量修改和导出权限。
- 固定没有导入权限。
- 全部字段可见；普通可编辑字段可编辑；自动编号、计算、表单只读和系统字段不可编辑。

### 6.6 查看全部数据 `VIEW_ALL`

- 可以查看当前租户当前表单的全部数据，并拥有预留的批量打印权限。
- 不能添加、复制、编辑、删除、批量修改、导入或导出。
- 全部字段可见且全部只读。

### 6.7 批量打印的最终规则

- 保留操作权限中的“批量打印”项及上表中的固定勾选状态。
- 自定义权限编辑器也保留“批量打印”选项。
- 默认工具栏、选中数据后的工具栏和“批量操作”菜单均不显示打印入口。
- 当前它只是预留能力，不应通过隐藏路由、快捷键或直接调用形成可用入口。
- 未来开发打印功能时必须复用现有 `batch_print` 权限校验，不能默认向所有用户开放。

## 7. 自定义权限组

新建或编辑自定义权限组时，保持“对成员发布”和“成员权限”区域不变，在权限下拉框下方展开编辑器；左侧固定包含：

1. 名称信息
2. 操作权限
3. 字段权限
4. 数据权限

### 7.1 名称信息

- 名称必填，在当前表单内不得重名。
- 描述选填。
- 名称和描述均允许修改。

### 7.2 操作权限

提供以下权限：

- 查看
- 添加
- 复制
- 编辑
- 删除
- 批量打印
- 批量修改
- 导入
- 导出

规则：

- 新建自定义权限默认只勾选“查看”。
- “全选”支持全选、半选和未选三种状态。
- 编辑、删除、复制、导出、批量修改依赖查看权限。
- 取消查看时同步取消依赖权限，或阻止保存并明确指出冲突。
- 是否显示操作入口必须同时受权限与当前产品能力控制；批量打印遵守预留规则。

### 7.3 字段权限

使用三列表格：

```text
字段 | 可见 | 可编辑
```

- 新建自定义权限时所有字段默认未勾选。
- 勾选“可编辑”时自动勾选“可见”。
- 取消“可见”时同步取消“可编辑”。
- 表单定义为只读、自动编号、计算或系统生成的字段不能勾选可编辑。
- 创建人、创建时间、更新人、更新时间可配置是否可见，但永远不能编辑。
- 支持字段搜索。
- “全选—可见”和“全选—可编辑”分别支持全选、半选和未选。
- 字段较多时列表内部滚动，表头固定。
- 必填业务字段保留必填标识，但字段权限不能绕过表单本身的只读约束。

### 7.4 数据权限

允许配置：

- “所有”或“任意一个”的单选控制，用于确定多条条件是全部满足还是满足任意一条。
- 一条或多条 `字段 → 运算符 → 值` 条件。
- 添加和删除条件。

规则：

- 运算符和值编辑器必须根据字段类型变化。
- 文本、数字、日期、字典、成员、部门等字段使用各自合法运算符。
- 当前用户等动态值由后端解析，不信任客户端传入的用户 ID。
- 条件由后端编译成参数化安全查询，禁止接受客户端 SQL、表达式代码或任意字段名。
- 如果权限包含查看、编辑、删除、导出或批量操作，必须有明确且可验证的数据范围；界面中的“全部数据”也要转换为显式的受租户和表单限制的后端范围。

### 7.5 保存校验

保存前检查：

- 名称已填写且不重复。
- 至少选择一个操作权限。
- 选择查看时至少一个字段可见。
- 选择编辑时至少一个字段可编辑。
- 数据权限条件完整且类型合法。
- 授权成员、部门或角色不为空。
- 系统字段未被授予编辑权限。

校验失败时停留在对应标签，突出显示问题，不得创建半成品权限组。

### 7.6 确认按钮与保存可靠性（强制）

权限创建、编辑、复制、启停、删除及成员调整的“确定”都必须是可验证的真实提交，不得出现点击无反应、静默失败或前端假成功。

- 点击“确定”时先使用同步单航班锁阻止同一次交互重复进入，再设置加载状态；不能只依赖异步状态渲染来防双击。请求完成或失败后必须释放锁。
- 客户端校验失败时切换到对应标签，在弹窗内显示可定位原因；服务端失败时同时显示弹窗内错误和全局提示。任何失败都保留草稿、所选对象和弹窗，不得静默关闭。
- 只有服务端返回成功、事务已经提交，并且当前权限组列表重新读取成功后，才显示成功提示和关闭弹窗。不得在请求发出、审计未写入或刷新失败时提前提示成功。
- 最终创建必须使用一个 Application Command 和一个数据库事务，同时写入权限组、操作权限、字段权限、数据规则、授权对象和审计；任一步失败全部回滚，禁止留下半成品权限组。命令映射必须显式填充每条权限明细的权限组/技术角色外键，不得依赖 ORM 从无关系对象的普通字面量中推断 `role_id`。
- ORM 保存必须明确实体目标。TypeORM 中，当对象可能来自 `save(Entity, object)` 的返回值、解构、复制或 DTO 映射时，必须继续使用 `manager.save(Entity, value)`，不得改成依赖运行时原型的 `manager.save(value)`；权限组技术角色统一使用 `manager.save(Role, role)`。
- 控制器不得直接操作数据库；异常不能被空 `catch`、未等待的 Promise 或仅写日志后吞掉。接口对校验错误、同名冲突、并发冲突和服务端错误分别返回可理解的 4xx/409/5xx 响应。
- 每个保存入口必须有成功、服务端失败、连续双击和事务回滚测试。测试至少有一层使用真实 ORM 契约或会拒绝“无实体目标保存、权限明细缺少外键”的严格替身，避免宽松 mock 掩盖 `CannotDetermineEntityError`、`role_id` 非空约束错误一类生产故障。

## 8. 后端安全边界

### 8.1 每个请求的校验顺序

按以下顺序执行：

1. 验证登录身份、用户状态和租户。
2. 验证表单归属和权限组启用状态。
3. 汇总成员、部门和角色带来的有效权限。
4. 校验请求动作。
5. 应用数据范围。
6. 应用字段可见与可编辑规则。
7. 执行业务校验、并发校验和写入。
8. 写审计并发布经过裁剪的实时事件。

标准业务表的写入资格由操作权限、字段权限、数据范围、租户范围和业务状态共同决定。除非产品需求明确规定“仅系统管理员”，不得再以 `isSystemAdmin`、模块管理员身份、角色名称或权限组显示名称作为额外硬编码门槛；拥有明确授权的普通用户必须按同一规则执行新增、修改、批量修改和导入。

### 8.2 数据泄露防护

- 无查看权限的字段不得出现在 API JSON、WebSocket、导出、复制内容、审计详情、错误信息或统计结果中。
- 无编辑权限的字段写入必须被后端拒绝或按明确策略忽略，并返回可定位的字段错误。
- 只读控制不能依赖 disabled 样式、隐藏按钮或前端路由。
- 根据 ID 读取、批量修改、导出和删除时仍要重新应用数据范围，防止通过伪造 ID 越权。
- 所有查询必须包含租户边界；超级管理员能力也应通过明确的后端策略授予。
- 默认拒绝未知动作、未知字段、未知权限组类型和无匹配授权。

### 8.3 审计

下列行为必须记录操作人、时间、租户、表单、权限组、请求来源、请求 ID、变更前和变更后内容：

- 权限组新增、复制、改名、删除、启用和停用。
- 成员、部门和角色的新增或移除。
- 操作权限、字段权限和数据权限变更。
- 数据新增、修改、删除、批量修改、导入和导出。
- 预置权限组的越权修改尝试。

敏感或无查看权限的字段在审计展示中仍须脱敏或裁剪。

## 9. 建议的数据模型约束

复用现有模型时确保至少能表达：

- `permission_groups`：租户、表单、内部类型、显示名称、说明、是否预置、是否启用、排序、版本。
- `permission_group_subjects`：权限组、对象类型、对象稳定 ID；建立防重复唯一约束。
- `permission_group_operations`：自定义组的操作授权；预置组由服务端常量或受控种子定义。
- `permission_group_fields`：字段可见、可编辑，引用稳定 `field_key`。
- `permission_group_data_rules`：条件组、所有/任一、字段、运算符、类型化值。
- `audit_logs`：完整变更上下文与不可变时间线。

数据库约束必须阻止：

- 跨租户引用。
- 同一权限组重复添加同一授权对象。
- 同一表单自定义权限组重名。
- 预置内部类型在同一表单重复。
- 可编辑为真但可见为假。

不要让数据库中的可编辑 JSON 成为预置权限的唯一真相；预置矩阵必须由不可随意修改的服务端规则约束。

## 10. 接口行为

- 同一业务资源的新增、单条修改、批量修改、Excel Preview、Excel Confirm 与其他 API 写入必须复用统一的字段规范化和业务校验；不得分别复制不同版本的必填、数值范围、字典、关联或跨字段规则。Preview 不得弱于最终 Application Command，Confirm 仍须重新校验权限、版本和全部业务规则；数据库 `NOT NULL`、`CHECK`、`FK`、`UNIQUE` 继续作为最终完整性防线，正常输入错误应在 Application 层转换为可理解的业务错误。
- 同一个标准业务字段的网页名称、Excel 模板名称、Excel 导出名称和 Excel 导入识别必须复用统一 `field_key` 与现行 `field.label`。兼容历史模板时可以维护显式 alias，但当前网页、新模板和新导出只能使用现行标准名称。

- 读取预置权限组时返回可展示的权限快照和 `readOnly` 标识。
- 更新预置权限组时只接受 `display_name`；携带其他受保护字段时返回明确错误或完全忽略，但全系统采用一致策略。
- 添加成员两步流程在最终确定前只保存在前端草稿状态；最终提交使用一个事务性命令。
- 权限提交接口必须返回已持久化记录的稳定 ID 和版本；前端提交后重新读取当前表单权限组列表，只有确认结果可见才结束保存流程。
- 批量接口逐条做租户、数据范围、字段和版本校验，返回逐项结果。
- 导入采用“上传/解析 → 预览 → 确认写入”，并使用幂等键；预置权限组当前全部禁止导入。
- 整个项目所有业务表的 Excel 导入必须统一使用“记录ID + 版本”判定写入方式：两列同时留空表示新增，由服务端生成记录ID并从初始版本开始；两列同时填写表示更新，必须使用系统导出值并执行乐观锁校验；只填写其中一列必须拒绝并明确提示“新增时记录ID和版本都应留空；更新时必须同时填写”。不得为某张表另设相反规则，也不得把空白记录ID误判为格式无效。
- “记录ID”和“版本”必须出现在导入模板及导出文件的填写说明中，明确解释含义、填写方式和是否必填。新增行要求当前表单同时具备 `import` 与 `create` 权限；更新行要求 `import` 权限，并在预览与确认时重新校验字段权限、数据范围和版本。前端隐藏入口不能替代后端校验。
- 同一个文件可以混合新增行和更新行，确认时必须在同一事务中提交；任一行失败则整批回滚。新增行必须按租户和稳定业务唯一键防重，已存在的业务记录应提示用户先导出并保留记录ID和版本后更新，不得静默重复新增或猜测为更新。确认结果必须分别返回并展示新增数和更新数，逐行写入审计并保持幂等。
- 所有表格文件导入必须在 Excel/CSV 解析前调用平台统一的加密文件检测，覆盖企业加密容器、Microsoft Office 加密复合文档和带加密标志的 ZIP/XLSX。检测到加密时立即停止解析和写入，用户提示必须原样为：`该文件被加密,请解密后再导入.`；不得把已识别的加密文件笼统提示为损坏、格式错误或模板错误。
- 表内“从另一业务表导入/同步”属于内部手工导入：只能由具备当前表单 `import` 权限的用户主动点击触发，不得在打开页面、切换日期、进入编辑模式或定时任务中自动执行。后端使用一个 Application Command 和事务完成读取、匹配、写入与审计，控制器和前端不得直接拼接数据写库。
- 内部手工导入必须先定义稳定业务匹配键，不得只按会随版本变化的来源行 ID 匹配。重复执行时按业务键区分“匹配、新增、更新、未变化、移除/保留”，只更新确有变化的来源字段，并保留报工数量、人工评审交期等明确由用户维护的字段。
- 以“当天、当周、当月”决定目标范围时，由服务端按 `Asia/Shanghai` 计算并验证目标周期；不得信任客户端传入的当前日期或任意目标周次。没有对应周期或来源为空时明确拒绝，不得误写其他周期或用空来源清空现有数据。
- 内部手工导入完成后返回并展示匹配、新增、更新、未变化及清理/保留数量；操作审计同时记录来源表、目标表、目标周期、匹配键和上述统计。已有人工作业数据的来源缺失记录不得静默删除。
- 导出内容按当前用户的数据范围和字段可见权限裁剪。

### 10.1 主计划表格稳定契约

- 主计划业务字段跨数据库、API、Web、权限、导入导出和同步时必须使用稳定英文 `field_key`；中文标题只负责显示，改名不得改变字段身份。禁止通过中文近似匹配、缩写或猜测字段。
- 事业部/部门在数据库和写接口中只保存组织稳定 UUID。主计划自身的组织选项接口必须按被操作资源的表权限和部门字段权限授权，不得借用月度计划、旧计划或其他表权限。
- 主计划 Excel 的事业部输入允许稳定 UUID、唯一部门名称或完整组织路径；重名必须拒绝并返回候选完整路径。导出统一显示完整组织路径，原文件再次导入必须解析回同一 UUID。
- 主计划 `orderDate` 是跨数据库、API、权限、Excel 和同步的稳定字段键，业务用户界面固定显示“下单日期”；不得因显示名称调整而改键。新版主计划业务用户侧只使用 `customerCode`，metadata、页面、权限字段、筛选、Excel 和业务投影不得暴露 `customerName`；ERP 原始层和 canonical 兼容字段可以内部保留。
- 有限枚举选项必须只有一个服务端权威定义，后端校验、metadata、UI 和 Excel 下拉共同消费；不得分别维护 `allowedValues`、前端字典和模板选项等多套值。
- 主计划默认只读。用户显式进入编辑模式后，拥有当前字段编辑权限且当前记录位于其更新数据范围内时，单元格才可编辑；失焦、Enter 或 Tab 只 PATCH 已变化字段并携带 `expectedVersion`。成功使用服务端确认值及最新版本更新缓存，失败恢复旧值并显示明确错误。表内编辑与批量修改必须同时保留。
- 报工类资源必须包含只读事业部字段并继承来源计划的事业部；查询、筛选、导出、字段权限和数据权限使用该稳定事业部 ID。同步不得用空值或旧来源覆盖人工报工内容。
- KDOS 正式工序只有唯一一份 10 工序 registry（KN-PROC-001）：`cutting 下料、machining 机加、bending 折弯、spotWelding 点焊、welding 焊接、woodworking 木作、grinding 研磨、blank 毛坯、surfaceTreatment 表面处理、packaging 包装`，顺序固定，毛坯位于研磨之后、表面处理之前（order 8，周期字段 `blankDays` / 数据库列 `blank_days`）。工序下拉、字段权限、工序周期表、倒排计划、周计划/月度计划工序分组、待报工与实际报工都必须从 `@tracker/shared` 的这份定义派生，不得再维护第二份工序名单或顺序。
- 旧 Planning 的 14 个 legacy process definitions（drawingBom、metalMain、woodMain、frontParts、woodwork、painting、acrylic、bakingPlating、rearPackingParts、assemblyPacking 等）已彻底退役：不得再作为新功能依据、不得出现在任何下拉或模板中、不得因为历史 Planning 而保留两套工序定义；`mps_process_cycles` 等正式表只保留 10 工序周期列，历史表数据按原样留存但不再正式读取。
- 生产执行报工闭环必须遵守以下固定规则（KN-PR-001 确认）：
  - 工序报工表的“待报工任务”（PENDING）来自 `mps_weekly_process_plans`（待执行工序任务），不是 `mps_process_reports`；PENDING 行的 `id` 是工序任务 ID，实际报工记录的 `id` 是报工记录 ID，两者不得混用。禁止为了“让实际报工有数据”预先插入空白报工或伪造零数量报工。
  - PENDING 字段顺序固定为：订单编号、品项编码、品项名称、工序、计划数量、累计报工、剩余数量、本次报工数量、生产日期；只有“本次报工数量”“生产日期”可填写，其余为任务上下文只读；页面与待报工 Excel 模板必须共用同一份权威字段定义，不得各写一份。
  - PENDING 行内填报与导入的业务语义都是 CREATE 一条新的实际报工记录（按 `weeklyPlanId` + `processCode` 定位任务，服务端补齐事业部/订单/品项/交期/计划数量/工序名称等来源快照），不是 UPDATE 工序任务；权限按 `mps-process-reports` 的**新增**权限判定，不能拿修改权限顶替，也不能接受前端自带来源快照或跨事业部伪造 `weeklyPlanId`。
  - 同一 `weeklyPlanId` + `processCode` 允许任意多次实际报工（同一天多笔也允许），每条都是独立执行事实；不得用日期或累计唯一约束把它们压成一条。
  - 累计报工与工序状态必须每次都按实际报工重新汇总（`SUM(production_quantity)`，剩余 = `GREATEST(计划 - 累计, 0)`），禁止在旧累计上做增量加减。累计 ≥ 计划即判完成并退出待报工列表，低于计划则重新出现；超计划不阻断录入，剩余最低显示 0。
  - 实际报工的所属周计划与工序是身份字段：创建时必须提供，生成后普通行内编辑、批量修改、导入更新都不得修改；生产日期与报工数量属于可纠错事实，修改或删除后必须重新汇总并同步到事业部周计划。
  - 计划同步只允许刷新实际报工里的来源快照（事业部/订单/品项/交期/计划数量），绝不能覆盖人工生产日期与报工数量。
  - 报工页面不得新增独立“操作”列；提交动作放在现有编辑模式与工具栏，报工保存后必须用真实对账结果（execution-rollup 状态）刷新事业部周计划/月度计划，不得用定时器猜测同步完成。
- 生产方式决定执行表：`自制` 不生成外协任务、生成工序任务；`中心外购` 生成外协任务、不生成工序任务；`外协` 生成外协任务、不生成工序任务；`自制+外协` 同时生成外协和工序任务。实际工序报工记录只能由真实报工提交创建，待报工任务保留在周计划工序任务表，禁止伪造零数量报工记录充当任务。
- **记录完整性与流程准入必须分离**：仅在进入下一业务阶段前必填的字段不得配置为每次 PATCH 都必须满足的 `requiredAlways`。准备/草稿阶段必须允许逐字段保存、逐步完善；流程推进时才由后端统一校验准入字段。准入字段列表、缺失项计算和同步筛选必须来自单一权威定义；页面只能解释该定义，Application、Sync Service 和 SQL 不得各自维护不同字段列表。
- 事业部周计划只能由满足准入条件的事业部基础计划生成，禁止网页直接创建和 Excel 直接导入新增；同一租户内一条基础计划最多对应一条周计划。派生记录必须以稳定父 ID 建立身份：周计划通过 `base_plan_id` 定位，技术、主材、外协和周计划工序通过 `weekly_plan_id` 定位；订单编号、品项编码、品项名称、交期编码和事业部等可修改业务字段仅是冗余快照。父业务字段变化时更新既有周计划及子快照，不得重建第二套子记录，自动同步不得覆盖人工报工、人工交期、状态、异常说明、责任人或附件。
- 事业部基础计划上的周计划状态（待完善/已具备条件/已进入周计划）、缺失准入项和生成失败反馈必须由同一个准入字段定义与 `base_plan_id` 关系计算，空字符串与 `NULL` 一律视为缺失，不得在页面、Application 或 SQL 中另写一份字段清单；“查看周计划”只能按稳定 `base_plan_id` 精确定位，禁止按订单编号、品项编码或交期编码模糊查找。基础计划保存成功与周计划生成失败必须分开反馈：业务写入已提交时不得回滚或显示为保存失败，兑现由独立 reconciliation 事件重试，并向用户明确提示“基础计划已保存，但周计划生成失败：原因”。

## 11. 最低验收测试

至少覆盖以下场景：

1. 五个预置权限的操作矩阵、字段状态和数据范围与本文完全一致。
2. 改名后内部权限不变；尝试修改预置权限其他字段被后端阻止。
3. `ADD_MANAGE_OWN` 用户无法通过列表、详情、批量接口、导出或伪造 ID 访问他人数据。
4. `ADD_VIEW_ALL` 能新增和查看全部数据，但不能修改已有数据。
5. `VIEW_ALL` 只能查看；`ADD_ONLY` 提交后不能进入数据管理页查看记录。
6. 系统字段无法通过任何入口修改。
7. 成员、部门和角色权限正确叠加；停用一个组不影响其他组贡献的权限。
8. 用户离职、停用或移出租户后立即失去有效权限，历史审计仍可追溯。
9. 返回第一步重新选择授权对象时，原选择和自定义权限草稿不丢失；取消后不落库。
10. 权限变更后缓存立即失效，实时广播不泄露无权字段。
11. 三处工具栏都没有批量打印入口，但权限定义仍保留。
12. 并发更新产生可理解的冲突响应，不静默覆盖。
13. 只读浏览模式下不会自动出现可执行的批量修改；进入编辑模式且同时拥有 `batch_update` 权限后，选择记录才可打开批量修改弹窗。
14. 弹窗显示准确的选中数量和 `50000` 条上限；不支持字段、四个系统字段、只读字段和无编辑权限字段不会进入候选项。
15. 伪造记录 ID、`field_key`、版本或筛选快照无法越过租户、数据范围、字段权限和乐观锁；部分失败返回逐项原因且不被显示为全部成功。
16. 批量修改成功后只更新“更新人、更新时间”，审计历史能够按 `batch_id` 追溯变更前后值，重复幂等请求不会再次修改数据。
17. 新建自定义权限从选择成员到最终确认完整落库，返回稳定 ID/版本，权限组、授权对象、权限明细和审计处于同一事务。
18. 连续点击两次“确定”只产生一个提交请求和一份审计；按钮在保存期间加载且不可再次触发。
19. 服务端保存失败时弹窗保持打开，授权对象、名称、四类自定义配置和当前标签不丢失，弹窗内显示服务端原因，数据库无半成品数据。
20. 严格 ORM 契约测试会拒绝缺少实体目标或权限组/技术角色外键的保存；TypeORM 普通对象保存不会再次触发 `CannotDetermineEntityError` 或 `role_id` 非空约束错误。
21. 勾选上级部门后，该部门、全部后代部门、各层级成员及直接挂在上级部门且没有子部门归属的成员全部默认选中；已选数量准确，后端有效授权范围与界面级联结果一致，且不会生成重复授权关系。
22. 父子层级或不同分支存在同名部门时，选择结果仍以部门 ID 区分；选择同名子部门能够得到该节点本身和完整子树成员，不会误含父部门的其他直属分支。旧通讯录省略连续同名层级时能解析到最深唯一节点，同深度多候选必须失败并报告歧义。
23. 角色按部门授权后，数据库只保存角色与所选部门稳定 ID，不生成该部门当前成员的静态角色关系；成员调入或新入职后自动获得角色，调出、离职或停用后下一次受保护请求立即失去角色，直接成员授权不受部门关系移除影响。
24. 所有标准业务记录表在只读浏览模式下仍提供最左侧 checkbox 选择列，能够单选、多选、当前页全选、清空选择，并使用稳定记录 ID 保持跨页选择；排序、分页和筛选不得造成选择串行或静默扩大选择范围。
25. 选择记录本身不授予编辑、删除、批量修改、导出或其他写权限；未进入编辑模式时，即使用户拥有 `batch_update` 权限并已选择记录，也不得执行批量修改。
26. 所有独立业务表格默认不显示固定“操作”列；需要行级动作时使用受权限和业务状态控制的紧凑 `⋯` 更多菜单，且该菜单及其状态不得进入数据库、字段注册、字段权限、导入模板或导出字段。
27. 用户进入编辑模式、拥有 `batch_update` 权限并至少选择一条可管理记录后，批量修改入口才显示和启用；退出编辑模式后选择可以保留，但批量修改入口必须立即失效。

## 12. 禁止事项

- 不得根据中文显示名称判断权限组类型。
- 不得把用户名或姓名当作授权主键。
- 不得把部门显示名称、名称数组或拼接后的名称路径当作部门身份或授权主键。
- 不得让前端决定“当前用户”或租户范围。
- 不得仅靠灰色控件、隐藏按钮或路由守卫实现安全。
- 不得把无权字段先返回前端再隐藏。
- 不得使用无返回反馈的确认按钮、空异常处理、未等待提交或只靠 React 异步状态防重复提交。
- 不得对可能是普通对象的 TypeORM 数据调用无实体目标的 `manager.save(value)`。
- 不得保存缺少权限组/技术角色外键的权限操作或字段权限明细。
- 不得给五个预置权限增加导入能力。
- 不得在任何工具栏或批量菜单中增加批量打印入口。
- 不得把 `null`、空字符串和 0 当成同一个值。
- 不得为了局部功能破坏现有主计划双层表头、字段键、审计、乐观锁或实时协同机制。
- 不得把 checkbox、选中状态、`selected`、`checked` 或“操作”作为普通业务字段持久化到数据库。
- 不得把进入编辑模式作为显示记录选择 checkbox 的前置条件。
- 不得默认给所有业务表增加固定“操作”列；需要行级操作时使用紧凑 `⋯` 更多菜单，并继续执行完整权限与业务校验。
